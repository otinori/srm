## そもそも何をするツールなのか

パソコンの中で何かソフト（アプリ）を動かすとき、そのアプリは基本的に「パソコンの中の
どこでも触れる」状態で動きます。普段使っているアプリの多くは信頼できるものなので問題に
なりませんが、次のような場面では不安が残ります。

- AIエージェント（指示に従って実際にファイルを操作したりコマンドを実行したりしてくれる
  AI）に、まとまった作業を任せたい
- 素性がよく分からない、または挙動を完全には把握できないプログラムを試してみたい

こうした場面で、「このフォルダの中でだけ作業させたい」「このフォルダの外は絶対に触らせ
たくない」「インターネットにはこの相手としか通信させたくない」という制限をかけて動かす
のがSRMです。制限は設定ファイル（後述の「ポリシー」）で決め、SRMがOS（Windows）の機能を
使って強制します。アプリ側を改造する必要はありません。

## 「コマンドライン」「PowerShell」とは

普段パソコンを操作するときは、アイコンをダブルクリックしたり、メニューから項目を選んだり
すると思います。これに対して「コマンドライン」は、**文字で指示を打ち込んで操作する画面**
です。SRMはこのコマンドラインから操作します。

Windowsには「PowerShell」というコマンドラインの画面が標準で入っています。開き方：

1. スタートメニューを開き、「PowerShell」と入力する
2. 表示された「Windows PowerShell」を**右クリック**し、「管理者として実行」を選ぶ
   （「管理者として実行」の意味は次の節で説明します）

開くと、黒い（または青い）画面に `PS C:\Users\あなたの名前>` のような文字が表示されます。
ここにコマンド（文字の指示）を入力してEnterキーを押すと実行されます。

## 「管理者権限」とは

Windowsのアプリは、普段は「このパソコンの持ち主が許可した範囲」でしか動けないように
なっています。ネットワークの通信ルールを変更したり、他のアプリの動きを制限したりする
ような、パソコン全体に影響する操作をするには、一段階強い権限（**管理者権限**）が必要です。

SRMは「アプリを閉じ込めて動かす」ためにこの強い権限を使う場面があるため、`srm run`や
`srm stop`などの一部のコマンドは、**PowerShellを「管理者として実行」した状態でないと
動きません**（前節の手順2で管理者として開くのはこのためです）。管理者権限なしで実行すると、
エラーメッセージが出てすぐに止まります。壊れているわけではないので、PowerShellを管理者
として開き直せば解決します。

## 「YAMLファイル」とは

SRMでは、「このアプリはどのフォルダに触れてよいか」「どの相手と通信してよいか」といった
設定を、`.yaml`という拡張子のテキストファイルに書きます。これを**YAML（ヤムル）ファイル**
と呼びます。難しいプログラミング言語ではなく、メモ帳でも開ける、次のような見た目の
ただのテキストです。

```yaml
name: my-app
filesystem:
  allow_paths:
    - path: "C:\\Users\\me\\Projects"
      access: rw
```

インデント（行頭の空白）で構造を表す点だけ注意すれば、上から順に読めば意味が分かるように
作られています（`allow_paths`＝「アクセスを許可する場所」、`access: rw`＝「読み書き両方
許可」など）。書き方の全項目は[usage.mdのポリシーファイルリファレンス](usage.md#ポリシーファイルリファレンス)
にまとまっています。

YAMLを直接書くのが不安な場合は、`Srm.PolicyEditor.exe`という、フォームに入力していく
だけで設定ファイルを作れる別アプリも同梱されています（詳細は
[src/Srm.PolicyEditor/README.md](../src/Srm.PolicyEditor/README.md)）。

## 「ポリシー」とは

前節のYAMLファイル1つ1つを、SRMでは**ポリシー**と呼びます。「このアプリをどういう制限で
動かすか」を決めた設計図、という意味です。`policies\`フォルダの中に、アプリ1つにつき
1つのポリシーファイル（例: `policies\my-app.yaml`）を置きます。

## 実際に動かしてみる

ここまでの用語が分かれば、[README.mdのクイックスタート](../README.md#クイックスタート)
がそのまま読めるはずです。念のため、最初の1つのコマンドだけ言葉で追ってみます。

```powershell
.\srm.exe validate smoke-test
```

- `.\srm.exe` — 同じフォルダにある`srm.exe`（SRM本体のプログラム）を実行する、という意味
- `validate` — SRMに用意されている「動作」の1つ。「検証する」の意味で、実際にアプリを
  動かす前に、ポリシーファイルの書き方が正しいかだけを確認する
- `smoke-test` — 対象となるポリシー名（`policies\smoke-test.yaml`というファイルに対応）

慣れないうちは、実際にアプリを動かす`run`の前に、必ず`validate`で書き間違いがないかを
確認する習慣をつけると安心です。

## 用語ミニ辞典

以降README.md・usage.mdを読む中で出てくる、よく使う言葉をまとめます。

| 用語 | かんたんな意味 |
|---|---|
| プロセス | 動いているアプリ1つ1つのこと。1つのアプリが裏でいくつも「子プロセス」を作ることもある |
| PID | プロセスに割り振られる番号（Process ID）。`srm list`などで確認できる |
| ポート/ホスト名 | 通信相手を指定する情報。`allow_hosts`には`api.example.com`のような相手先の名前を書く |
| ログ | SRMやアプリが「何をしたか」を記録したファイル。何か不具合があったときに確認する |
| サンドボックス | 「砂場」の意味から転じて、外に影響を与えないよう区切られた実行環境のこと。SRM全体のコンセプトそのもの |
| Tier1 / Tier2 | SRMが用意している隔離の強さの段階。Tier1は同じパソコンの中で制限をかける方式、Tier2はWindows Sandboxという仮想的な別のパソコンごと切り離す、より強い方式 |
| AIエージェント | ChatGPTやClaude Codeのように、指示に応じて実際にファイル操作やコマンド実行まで行うAI |
| MCP | AIエージェントがSRMのような外部ツールを呼び出すための共通の仕組み（Model Context Protocol）。README.mdの「MCPサーバー」の説明で登場する |

## 困ったときは

- エラーメッセージが出た場合は、まず[usage.mdのトラブルシューティング](usage.md#トラブルシューティング)
  に同じ文言がないか探してください。よくある原因と対処法がまとまっています。
- 「管理者権限が必要」というエラーが出た場合は、[「管理者権限」とは](#管理者権限とは)の
  手順でPowerShellを開き直してください。
