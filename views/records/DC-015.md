# [DC-015] Tier2のネットワーク制御はゲスト内AppContainer SIDベースWfpManagerを正とする（DC-011改訂）

## Context

DC-011はTier2のネットワーク制御をWindows Sandboxの仮想スイッチ境界
（Hyper-V Firewall）で行うと決定し、「PoCでHyper-V FirewallがWindows
Sandboxのゲスト通信を実際にフィルタできないと判明した場合、ゲスト内WFP相当の
実装に切り替える」というreview_triggerを設定していた。2026-07-03、Windows
実機でこのPoCを実施した結果、以下3通りの手段すべてでWindows Sandboxの
ゲスト通信を制御できないことが判明した。
1. `Add-VMNetworkAdapterExtendedAcl`（Hyper-V VM Network Adapter拡張ACL）:
   `Get-VM`はWindows Sandboxを一切返さず、`Get-VMNetworkAdapter -All`が返す
   "Container NIC"は`VMName`が空で個々のSandboxインスタンスと対応付けできない
   上、そもそもAPI自体が「自動インターネット接続共有スイッチ（Default Switch）
   は変更できません」というエラーで拒否される。
2. `vEthernet (Default Switch)`にインターフェーススコープした通常のWindows
   Defender Firewallの`Outbound`ブロックルール: ルール自体は正しく作成・
   スコープされ有効化されたが（`Get-NetFirewallInterfaceFilter`で確認済み）、
   Sandbox内からのHTTPS接続は何の影響も受けず成功し続けた。
3. 同インターフェースへの`Inbound`ブロックルール（ゲスト→ホスト方向として
   試行）: 同様に効果なし。
Windows SandboxはHyper-V Manager配下の伝統的なVMオブジェクトモデルに乗って
おらず、WSL2等と同じ軽量コンテナ基盤（HCS）上で、恐らく通常のWFP評価層を
経由しない専用の高速パス（vSwitch拡張によるNAT転送）でネットワークを処理して
いると推測される。この結果、DC-011のreview_triggerが明示的に想定していた
状況に該当した。


## Decision

Tier2のネットワーク制御は、DC-011が当初却下した「ゲスト内でTier1と同じWFP
相当の仕組みを再実装する」方式に切り替える。具体的には、既存の
`WfpManager`（AppContainer SIDベースのallow_hosts→DNS解決→フィルタ登録
ロジック、DC-009）を新規開発せずそのまま再利用し、`RunCommand.RunNested`
（ゲスト内`srm.exe run --nested`）から呼び出す。ゲストも独立したOS
インスタンスとして自身のWFPエンジンを持つため、Sandbox境界向けの
バリエーション実装（DC-011のimplicationsが想定していたもの）は不要で、
Tier1向けに書かれたロジックがそのまま動作する。`.wsb`の`Networking`
Default/Disable切り替え（DC-012由来、provisionフェーズ用途と共用）は
Sandbox全体のネットワーク到達性という粗いスイッチとして引き続き使い、
ホスト/ドメイン単位の粒度はゲスト内WfpManagerが担う。


## Rationale

DC-011がこの方式を却下した理由（ゲスト内でSYSTEM権限相当を奪われた場合に
フィルタ自体を解除されうる）は依然として有効な懸念だが、実機PoCにより
DC-011が正としていたHyper-V Firewallによる代替がそもそも技術的に実現
不可能と判明した以上、「弱いが機能する防御」と「機能しない防御」の選択に
なった。ユーザーへの確認の結果、後者は受け入れられないため前者を選ぶ。
なお対象アプリ自体はDC-010の多層防御の中で既にAppContainer隔離下にあり、
ネットワークフィルタの解除にはそのAppContainer自体からの権限昇格が
別途必要になるため、「AppContainer隔離が破られない限りは有効」という
Tier1と同等の防御レベルには留まる（Sandbox境界を跨いだ多層防御という
DC-010の設計自体は変わらない。ネットワーク制御の実施層のみがSandbox境界
からゲスト内AppContainer境界に後退する）。


## Implications

- `SandboxLauncher`/`RunCommand.RunTier2`に予定していた「Sandboxの インターフェース/vswitch条件でのフィルタ登録バリエーション」の実装は 不要になった（DC-011のimplicationsを撤回）
- `RunCommand.RunNested`が`WfpManager.Install`/`RemoveForApp`をTier1と 同じ形で呼び出すよう変更した
- DC-011は本レコードにより実質的に改訂される（registry上はDC-011を Supersededとし、本レコードが後継）

## Rejected Alternatives

### Hyper-V Firewallでの実現を追求し続ける（回避策の探索） (alt-keep-hyperv-firewall)

「自動インターネット接続共有スイッチは変更できません」というエラーは
Microsoftが意図的に設けた保護であり、Windows Sandboxが内部的に使う
Default Switch特有の制約。回避する非公式な方法（レジストリ改変等）は
サポート外でOSアップデートによる破損リスクが高く、DC-005（既存の
サポートされた手段を優先する）に反する。


### Tier2のネットワーク制御を実装せず、VM全体のNetworking On/Offのみとする (alt-no-network-enforcement)

network.allow_hostsをポリシーで宣言してもTier2では一切効かない状態を
放置することになり、ユーザーの期待するセキュリティ境界と実装に乖離が
生じる。ユーザーへの確認の結果、機能する代替（ゲスト内WFP）がある以上
放置は選ばないと判断した。
