# [DC-008] 実行中アプリの追跡はJSONファイルレジストリ方式を採用（IPC・デーモンなし）

## Context

`srm list` と `srm stop <app>` は、別プロセスとして起動された `srm run` の
実行状態（アプリ名・PID・起動時刻）を参照できる必要がある。v0.1にはデーモン
プロセスや常駐サービスは存在せず、各CLI呼び出しは独立したプロセスとして実行される。


## Decision

`%ProgramData%\SRM\run\running.json` に実行中アプリの一覧をJSONとして書き込む
`RunningAppRegistry` を実装する。`srm run` が起動時にエントリを追加し、
`srm list`/`srm stop` はファイルを読み込んで参照する。`srm list` 実行時に
既に終了しているPIDのエントリは自動的に間引く（Process.GetProcessById +
HasExited チェック）。


## Rationale

v0.1のスコープは単一ユーザー・単一マシンでの利用が前提であり、複数プロセス間の
状態共有に名前付きパイプやソケットによるIPCを導入するほどの要件がない。
ファイルベースであれば実装がシンプルで、`%ProgramData%` のACLによる
保護も既存のセキュリティモデル（管理者のみ書き込み可）と一貫性がある。


## Implications

- 同時書き込み（複数 `srm run` の同時実行）に対する排他制御は未実装——v0.1では 同時起動の競合は許容範囲とみなす。v0.2でファイルロックの追加を検討する
- running.json が破損した場合のリカバリ手順が未定義——空配列として扱うなど のフォールバックを将来追加する余地がある

## Rejected Alternatives

### 常駐デーモン + Named Pipe IPC (alt-named-pipe-daemon)

実行中アプリの状態を正確にリアルタイム管理できる利点はあるが、
デーモンのライフサイクル管理（インストール・自動起動・クラッシュ復旧）
という新たな複雑性をv0.1に持ち込むことになる。v0.1のゴール（node.exeの
隔離実行）に対してオーバーエンジニアリング。


### Named Mutex + 共有メモリ (alt-mutex-shared-memory)

プロセス間の排他制御・データ共有は可能だが、JSONファイルより実装・
デバッグが複雑。v0.1で想定する同時実行数（数アプリ程度）では
ファイルI/Oのオーバーヘッドは無視できる。


## Review Triggers

- 複数ユーザー・複数マシンでの状態共有が必要になった場合（v0.2以降）
- 同時起動の競合が実運用で問題になった場合
