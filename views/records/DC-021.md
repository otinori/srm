# [DC-021] srm自体にカーネルCPUスタックトレース採取を内蔵（wpr.exe非依存、`srm diag --stacktrace`）

## Context

DC-016（claude-code CLIをAppContainer内で-p実行するとカーネルモードCPUを消費し続ける
未解決バグ）のreview_triggerには、具体的なカーネル関数・モジュールを特定するための
次のステップとして「WPR (Windows Performance Recorder) + WPA (Windows Performance
Analyzer) でCPUサンプリングスタックトレースを取得する」ことが挙げられていた。

実機でこの調査を実施したところ、`wpr.exe -start CPU -filemode`でのトレース開始は
成功するものの、`wpr.exe -stop`がBash・PowerShellどちらから呼んでも同一のCOM
アパートメントエラー（`Cannot change thread mode after it is set`、エラーコード
0x80010106）で失敗し、実際のトレースデータを`.etl`ファイルとして確定できないことが
判明した（回収できた一時ファイルは256バイトのヘッダのみのスタブで、実データを含まない）。
2回とも同じエラーが再現したため、シェル固有の問題ではなくこのマシン上のWPRセッション
周りの環境要因（Game Bar等の別プロセスがETWセッションを掴んでいる可能性等）と考えられ、
かつWPA（スタック解析GUI）自体もこの環境にはインストールされていなかった。

ユーザーから「今後、srmを起動すると同じ様に原因不明の問題が出てくる可能性がある。
srmに診断機能を実装できないか」との要望があり、外部プロセス（wpr.exe）に依存する限り
同じ環境要因で今後も同様の失敗が起こりうるため、wpr.exeを経由しない代替手段を
`srm`自体に内蔵する方針とした。


## Decision

`Microsoft.Diagnostics.Tracing.TraceEvent`（PerfView/dotnet-traceが内部で使うのと
同じMicrosoft製.NET ETW APIラッパー）を新規プロジェクト`Srm.Diagnostics.Kernel`
として追加し、`KernelCpuStackSampler`を実装した。`srm diag <app> --stacktrace
[--duration-ms] [--top]`として`srm diag`（DC-020）に統合した。

1. `Srm.Diagnostics.Kernel`は`Srm.Cli`からのみ参照する新規プロジェクトとし、
   `Srm.Runtime`・`Srm.Mcp`・`Srm.PolicyEditor`には依存を持ち込まない。
   `tools/package.ps1`が3つの実行ファイルを同一binフォルダへpublishする構成
   （DC-018で顕在化した共有依存のバージョン衝突リスク）を踏まえ、TraceEventという
   比較的大きな新規パッケージ依存をsrm.exeの publish 出力だけに閉じ込める。

2. `KernelTraceEventParser.KernelSessionName`でカーネルETWセッションを開始し、
   `Profile`（CPUサンプリング）・`ImageLoad`・`Process`キーワードを有効化する。
   `EnableKernelProvider`の`stackCapture`引数に`Profile`を明示的に指定しないと
   カーネルコールスタックが一切採取されない（実装時に実際に踏んだ罠。stackCapture
   省略時は`CallStack()`が常にnullを返す）。

3. シンボル解決は2パス方式にした。1パス目でシンボル解決せずにリーフフレーム
   （実行中だったコードアドレス）を集計し、実際にリーフフレームとして出現した
   モジュールの集合だけを求める。2パス目でその集合だけを対象に
   `SymbolReader`（Microsoft公開シンボルサーバー、`SymbolPath.MicrosoftSymbolServerPath`）
   でシンボル解決する。対象プロセスがロードしている全モジュールを無条件に解決すると
   （claude.exeのような多数のCOM関連DLLをロードするプロセスでは）実機で3分以上かかる
   ことが判明したため、この最適化が必須だった。

4. 対象は当面Tier1のみとする。Tier2（Windows Sandbox）はゲスト側が別カーネルで
   動作するため、ホスト側で開始したETWセッションではゲスト内プロセスのカーネル
   スタックを採取できない。Tier2対応は本changeのスコープ外とし、必要になれば
   ゲスト内`--nested`側で同様のETWセッションを開始する設計を別途検討する。

5. 通常の`srm diag`（CPU時間内訳・ページフォールト率、DC-020）とは異なり、
   `--stacktrace`はMCPツールとしては公開しない。管理者権限必須・初回シンボル
   ダウンロードで数十秒かかりうる・Tier1限定という制約から、対話的なAIエージェント
   操作にはそぐわない調査専用のCLIオプションと位置づける。

6. 【追加】DC-016の次の調査ステップ（「どの機能が名前付きパイプを作成しているか
   特定する」）をProcess Explorer等の手動GUI操作に頼らず`srm diag --stacktrace`に
   組み込むため、同じカーネルセッションで`FileIOInit`キーワードも有効化し、
   `FileIOCreateTraceData`イベントのFileNameから`\Device\NamedPipe\`配下のものだけを
   抽出・集計する`NamedPipesCreated`を結果に追加した。CPUサンプリングと同一の
   セッション・同一の採取時間内で完結させ、追加の採取往復は発生させない。


## Rationale

wpr.exeという外部プロセス・COMベースの制御チャネルに依存する限り、今回実際に踏んだ
環境要因（原因未特定のCOMアパートメント競合）が再発するリスクを構造的に排除できない。
PerfView/dotnet-traceが使っているのと同じ.NET ETW APIを直接使うことで、wpr.exeの
CLI層を完全にバイパスし、同じ失敗モードを回避した。実際、この方式でDC-016の
カーネル関数特定（`NtQueryInformationToken`・`NtCreateNamedPipeFile`等）に初めて
成功しており、有効性を実証済み。

新規プロジェクトとして切り出し`Srm.Cli`のみから参照する構成にしたのは、DC-018で
「複数の実行ファイルが同一binフォルダへpublishされる際の依存バージョン衝突」問題を
経験済みであり、TraceEventという比較的重い新規依存を`Srm.Runtime`（全アプリが参照）
に追加すると同じリスクを再導入するため。`Srm.Cli`だけがこの依存を持つ設計にすることで、
`Srm.Mcp`・`Srm.PolicyEditor`のpublish結果には一切影響しない。

シンボル解決を2パスに分けたのは、素朴に「ロード済み全モジュールを解決してから
サンプルを集計する」実装を最初に書いたところ、実機で3分のタイムアウトを超えても
終わらなかったため。claude.exe（Bunランタイム）はCOM関連DLLを含む数十のモジュールを
ロードしており、そのほとんどはCPUサンプルのリーフフレームには一切出現しない
（＝解決しても使わない）。実際に出現したモジュール（今回のケースではntdll.dll・
ntoskrnl.exeのみ）に絞ることで、数秒〜数十秒程度まで短縮できた。

Tier2を対象外としたのは、ホストが開始するETWセッションはホストと同じカーネルの
イベントしか見えず、別VM（Windows Sandbox）内のカーネルのイベントには原理的に
到達できないため。DC-020の`srm diag`（CPU時間内訳）がSandboxControlChannel経由で
ゲストに処理を委譲する設計を踏襲するなら、Tier2対応にはゲスト内`--nested`側で
同様のETWセッションを開始しホストへ結果を転送する仕組みが別途必要になるが、
今回のDC-016はTier1環境での再現のため優先度を下げ、スコープ外とした。

パイプ名特定を既存の`--stacktrace`セッションに相乗りさせたのは、CPUサンプリング
用のカーネルセッションを既に開いている以上、`FileIOInit`キーワードの追加コストは
ごく小さく、別コマンド・別採取往復にする理由がなかったため。実際に使ってみると
対象プロセスの完了イベントが0件という結果になったが、これ自体が「パイプ作成が
一度も成功していない」という新たな状況証拠になり、機能として無駄ではなかった
（DC-016参照）。

`--pid`オプションを追加したのは、DC-016の根本原因切り分けに「AppContainer隔離
あり/なしの対照実験」が必要になったため。`srm diag`は元々`RunningAppRegistry`
経由でsrm管理下のアプリしか対象にできなかったが、比較対象（隔離なしで直接起動
したclaude.exe）はsrmの管理外にある。同じ診断ロジック（`DiagCollector`・
`KernelCpuStackSampler`）はPIDさえあれば動くため、`RunningAppRegistry`を経由
しない直接指定の入口を追加するだけで対応でき、新規ロジックの実装は不要だった。
この対照実験により、DC-016の症状がAppContainer隔離環境固有であることが
ほぼ確定した（DC-016参照）。


## Implications

- 新規プロジェクト`src/Srm.Diagnostics.Kernel`（`Microsoft.Diagnostics.Tracing.TraceEvent` に依存、`Srm.Cli`からのみ参照）が追加された
- `srm diag`に`--stacktrace`・`--top`オプションが追加された（Tier1のみ、要管理者権限、 初回シンボルダウンロードで数十秒かかりうる）
- MCPツールとしては公開していない
- DC-016のcontext/learning/review_triggerに、実際に特定できた具体的なカーネル関数 （`NtQueryInformationToken`・`NtCreateNamedPipeFile`等）と次の調査ステップを追記した
- `CaptureResult`に`NamedPipesCreated`（名前・出現回数のリスト）を追加した。DC-016の 再現では常に空リストだったが、これは「パイプ作成が完了に至っていない」ことを示す 有効な結果であり、パイプ名を使った特定が原理的に不可能であることも同時に判明した
- `srm diag`に`--pid <pid>`オプションを追加した。`app`名の代わりに任意のPIDを直接 指定でき、`RunningAppRegistry`（srm管理下のアプリのみ追跡）を経由しないため、 srm run経由でないプロセス（比較用の非隔離実行等）も同じ診断ロジックで調査できる
- 自動テストは追加していない（実際の採取が管理者権限・実CPU負荷・シンボルサーバーへの ネットワークアクセスを要し、CI向けの高速・決定的なユニットテストにしにくいため。 調査専用ツールとしての性質を踏まえ、実機での動作確認のみで担保した）

## Review Triggers

- 【2026-07-15解決】Tier2（Windows Sandbox）向けに、ゲスト内`--nested`側で ETWセッションを開始し`SandboxControlChannel`（tier2-channel-c-mapped-folder の汎用request/resultプリミティブ）経由でホストへ結果を転送する設計を DC-027として実装・実機検証した。機構自体は正しく動作する（CPU高負荷 プロセスに対し実際にスタックフレームを採取できることを確認）が、 Tier1と比べて著しく遅い（実測でアイドル時約110秒、CPU高負荷時約14分） という重要な性能特性が新たに判明し、DC-027のreview_triggerへ持ち越した
