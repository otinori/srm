## Context

DC-016（`records/DC-016.yaml`）は、`claude-code` CLIをTier1（AppContainer）で
`-p`実行すると原因不明のカーネルモードCPU張り付き（ビジーループ）が発生する
未解決バグを記録している。review_triggerには「WPR+WPAでのスタックトレース
採取」「`process.allow_child_processes`/`network.allow_hosts`を変えた際の
症状変化確認」「コンテキストスイッチ数/秒・ページフォールト数/秒の計測」が
次の調査ステップとして挙げられているが、これらはいずれもProcmon・
Get-Counter・WPRを都度手動でRDP/コンソール越しに操作する必要があり、再現の
度に手間がかかる。

当初のユーザー要望は「ゲストとホストで通信する仕組みを実装し、その通信を
使って情報採取を容易にする」であったが、`policies/claude-code.yaml`は
`tier: 1`であり、Tier1にはTier2の`--nested`のような別プロセス（別VM）
としての「ゲスト」は存在しない。対象アプリはホストと同一セッション上で
直接動く、AppContainerトークンで隔離されたプロセスに過ぎない。確認の結果、
Tier1・Tier2の両方に対応する方針で合意した。


## Decision

実行中アプリのCPU時間内訳（ユーザー/カーネル）・秒あたりページフォールト数を
短時間サンプリングして返す診断機構（openspec change
`guest-host-diagnostics-channel`）を実装した。

1. サンプリング本体`DiagCollector`（`Srm.Runtime.Diagnostics`）は、対象PIDの
   CPU時間・ページフォールト数を指定した経過時間の前後でサンプリングし、
   差分から秒あたりレート・比率を計算する。ページフォールト数は
   `GetProcessMemoryInfo`（psapi.dll）へのP/Invokeで取得し、新規NuGet
   パッケージには依存しない。

2. Tier1（ホストと同一セッション）は、ゲスト↔ホストの往復を行わず、ホスト
   側から`DiagCollector`を直接呼び出す。AppContainer隔離はセキュリティ
   トークンの制限であり、プロセスの可視性自体はホストから常に見えるため。

3. Tier2（Windows Sandbox）は、対象プロセスが別VM上にあるため、
   `SandboxControlChannel`（DC-010）に追加した`diag-request.json`/
   `diag-result.json`という固定パス2ファイルの組（tier2-channel-a-focus-
   guaranteeの`focus-request.json`/`focus-result.json`と同じ、都度上書き・
   `requestId`不一致は無視するプロトコル）でゲスト内`--nested`へ委譲する。
   `RunCommand.RunNested`の`BlockUntilStop`ループに`onDiagRequestDetected`
   コールバックを追加し、フォーカス要求と同じrequestId差分検出ロジックを
   再利用した。

4. ホスト側の入口`DiagOperation`（`Srm.Runtime.Operations`）が
   `RunningAppRegistry`からTierを判定し、Tier1/Tier2を振り分ける。新規CLI
   サブコマンド`srm diag <app> [--duration-ms]`として公開し、DC-016のような
   実機調査時にのみ使う想定のためMCPツールとしては公開しない。


## Rationale

Tier1は「ゲスト」という概念自体が存在しないため、Tier2と同じ往復プロトコル
を持ち込むと複雑さが増すだけで得るものがない。プロセスの可視性はAppContainer
トークンによる制限を受けず、ホストから`Process.GetProcessById`で直接
アクセスできることを実機で確認した上で、Tier1は直接呼び出し、Tier2のみ
ファイルベースの往復にするという非対称な設計にした。

Tier2側のプロトコルをfocus-request/resultと同じ「固定パス2ファイル上書き」
方式にしたのは、DC-017が明示的に却下した`alt-percommand-file-queue`
（1コマンド1ファイルの積み上がるキュー）の問題を再導入しないため。
`BlockUntilStop`の既存のオーバーロード連鎖に追加する形にしたことで、
`onFocusRequestDetected`と全く同じrequestId差分検出ロジックを再利用でき、
新規の仕組みを発明せずに済んだ。

ページフォールト数の取得に`System.Diagnostics.PerformanceCounter`パッケージ
を使わなかったのは、DC-018で顕在化したように`Srm.Runtime.csproj`は
`tools/package.ps1`が複数の実行ファイルを同一binフォルダへpublishする都合上
パッケージバージョンの整合性がシビアであり、新規パッケージ依存を増やす
リスクを避けたかったため。BCL標準の`Process`クラスと単一の公開Win32 API
（`GetProcessMemoryInfo`）呼び出しのみで完結させた。

真のコンテキストスイッチ数/秒の取得（`NtQuerySystemInformation`等の非公開API
が必要）と、WPRによる完全なカーネルスタックトレース採取は本changeの
スコープ外とした。DC-016の根本原因特定に必要な精度は、まずカーネル時間比率・
ページフォールト率という軽量な指標を都度手動操作せず取得できるようにする
ことで既存のProcmon調査結果（9.1〜9.7、`records/DC-016.yaml`）を再現・
補強できるかを確認してから判断する方が、DC-017が温存した「チャネルC
（HvSocket）」のPoC結果を待たずに着手できると判断した。


## Implications

- `SandboxControlChannel`に`diag-request.json`/`diag-result.json`の読み書き メソッドと、`BlockUntilStop`の診断要求検出コールバックオーバーロードが 追加された
- `Srm.Runtime.Diagnostics.DiagCollector`（新規）・ `Srm.Runtime.Operations.DiagOperation`（新規）が追加された
- `RunCommand.RunNested`のメインループに診断要求ハンドラ （`HandleDiagRequest`）が追加された
- 新規CLIサブコマンド`srm diag <app> [--duration-ms]`が追加された （MCPツールとしては非公開）
- `records/DC-016.yaml`のreview_triggerに、本レコードへの相互参照付きで 「`srm diag`が利用可能になった」旨を追記した
