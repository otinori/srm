# [DC-022] Tier2ネスト実行のAppContainerラップにopt-outを追加し、WFPの識別子をAppContainer SID以外にも対応させる（DC-010改訂）

## Context

DC-016は、claude-code CLI（Bunでコンパイル）がAppContainerトークン下では
`NtCreateNamedPipeFile`が既定DACL（ALL APPLICATION PACKAGESが含まれない）により
内部的に失敗し続け、Bun/claude-code側のリトライロジックがこれを無限リトライして
カーネルモードCPUのビジーループになるという未解決バグを、srmが制御可能な
AppContainer設定要素（ケーパビリティSID・子プロセス制限・トークン既定DACL）を
総当たりで切り分けた末に、srm側からの修正手段が無いと結論づけた。

一方DC-010は、Tier2（Windows Sandbox）は常にゲスト内で`srm.exe run --nested`を
AppContainerでラップして起動する設計を採用しており（`alt-vm-only`＝VM境界のみは
明示的に却下済み）、DC-015はTier2のネットワーク制御（WFP）もこの同じAppContainer
SIDを条件に登録する設計にしていた。つまり現状のTier2実装のままでは、Claude Codeを
Tier2で動かしてもゲスト内で同じAppContainerに通されるため、DC-016のビジーループを
そのまま踏む可能性が高いことが、ユーザーとの議論の中で判明した。

これを受けて、プロジェクト憲章（環境を壊さない・情報を漏洩しない）に立ち返り、
「AppContainerによるfs/プロセスの厳密な隔離」と「VM境界+ネットワーク遮断による
最低限の隔離」を、単一の梯子ではなく、アプリごとに使い分け可能な独立した手段として
再整理する方針をユーザーと合意した。本レコードはこのうち、Tier2ネスト実行の
AppContainer依存を緩め、ネットワーク遮断をAppContainer非依存でも維持できるように
する部分（openspec change: tier2-guest-network-egress）の実装内容を記録する。
fsの隔離手段（制限付き専用アカウント+NTFS ACL）は別change
（restricted-account-app-isolation）として並行して起票され、本レコードのスコープ外。


## Decision

1. `PolicyModel`に`tier2.app_container`（既定`true`）を追加した。`false`にすると
   `RunCommand.RunNested`はAppContainerLauncherを一切経由せず、`Process.Start`相当
   （新規`LaunchWithoutAppContainer`）で対象アプリを直接起動する。ACL付与
   （`AclManager.GrantAccess`/`GrantExecuteAccess`）も行わない
   （AppContainerを使わない以上、fsの隔離は意図しておらず、VM境界のみに後退する
   ことを明示的な設計とする）。

2. `WfpManager`が登録するallow/blockルールの条件を、従来のAppContainerパッケージSID
   （`WfpIdentity.PackageSid`）単独から、`WfpIdentity`という識別子の型（PackageSid /
   UserSid / AppPath）に一般化した。`tier2.app_container: false`の場合は
   `WfpIdentity.FromAppPath(実行ファイルパス)`（`FWPM_CONDITION_ALE_APP_ID`、
   `FwpmGetAppIdFromFileName0`で解決）を使う。子プロセスを生成しない単一プロセス
   アプリ（`claude -p`のヘッドレス実行等）向けのフォールバックと位置づけている。

3. 【重要な否定的結果・修正】`WfpIdentity.UserSid`
   （`FWPM_CONDITION_ALE_USER_ID`、制限付き専用アカウントのユーザーSIDを条件にする、
   restricted-account-app-isolation change依存）は、当初
   `FWPM_CONDITION_ALE_PACKAGE_ID`と同じ生SID（`FWP_SID`型）で条件を組んだところ、
   実機で`FwpmFilterAdd0`が`FWP_E_TYPE_MISMATCH`（0x80320027）で失敗することを
   確認した。Microsoft公式サンプル「Permitting and Blocking Applications and
   Users」を調査し、`FWPM_CONDITION_ALE_USER_ID`は対象SIDに
   `FWP_ACTRL_MATCH_FILTER`アクセスを許可する自己相対セキュリティ記述子
   （`FWP_SECURITY_DESCRIPTOR_TYPE`、`BuildSecurityDescriptorW`で構築）を条件値に
   要求することが判明し、`WfpManager.BuildUserSidSecurityDescriptorBlob`として
   実装・修正した。修正後、実機のWFPエンジンに対する登録・削除・実際の接続の
   許可/拒否（`example.com`への接続を`allow_hosts`の有無で許可/拒否できること）を
   `WfpManagerTests`で確認済み。

4. `srm validate`は`tier: 2`かつ`tier2.app_container: false`のポリシーに対して、
   「AppContainerによるfs/プロセスの隔離は適用されず、Windows Sandbox（VM境界）と
   ネットワーク遮断のみが有効」という警告を表示するようにした（実機で表示内容を
   確認済み）。

5. DC-016の再現コマンド（`claude -p "Reply with exactly: PONG" --output-format
   text`）を、`LaunchWithoutAppContainer`と同じ起動方式（AppContainerLauncherを
   経由しないプレーンなプロセス起動）+ AppPath条件の`WfpManager`を有効にした状態で
   実機実行し、10秒未満で`PONG`を正しく出力して完了することを確認した（DC-016の
   非隔離ベースラインの約2秒と整合し、AppContainer隔離時の19分超のビジーループとは
   明確に異なる）。この検証はAnthropic APIへの実課金を伴う一回限りの確認のため、
   自動テストとしては残さず、本レコードに結果を記録することで担保する
   （DC-021のimplicationsと同じ方針）。

6. `WfpIdentity.UserSid`の実配線（`RunCommand.RunNested`のopt-outパスを制限付き
   専用アカウントで起動し、`UserSid`識別子でWfpManagerを呼ぶ部分）は、
   restricted-account-app-isolation changeのアカウント払い出し機構に依存するため、
   本レコードの時点では未実装のまま据え置く（openspec changeのtasks.md task 5）。


## Rationale

DC-016は「srmが制御可能なAppContainer設定要素はいずれも原因ではない」というところ
まで実機で切り分けを尽くしており、これ以上AppContainer自体の内部動作に踏み込む
調査を続けても、Bun/claude-code側の非公開コードに阻まれてsrmからは修正できない
可能性が高い。一方でTier2（Windows Sandbox）はVMの破棄可能性という構造的な保証を
既に持っており、AppContainerのfs/プロセス精度が無くても「環境を壊さない」という
憲章の一方の柱は成立する。残る「情報を漏洩しない」という柱のうち、ネットワーク
経由の漏洩はAppContainer非依存でWFPを効かせられれば防げるため、この部分を
切り離して先に実装できると判断した。

AppPath条件を先に実装しUserSid条件を後回しにしたのは、UserSid条件の実際の価値
（プロセスツリー全体を1ルールでカバーできる）は制限付き専用アカウントという
トークン継承の仕組みがあって初めて意味を持つため。そのアカウント払い出し機構
（restricted-account-app-isolation）が無い現時点でも、単一プロセスで完結する
`claude -p`のようなヘッドレス実行はAppPath条件だけで実用上十分にDC-016の
ユースケースをカバーできるため、依存関係の無いAppPathを先に倒す方が早く価値を
出せると判断した。

UserSid条件の型不一致（FWP_SID→FWP_SECURITY_DESCRIPTOR_TYPE）は設計段階の
ドキュメント（design.md）に書いた仮説が実機検証で誤りと判明した典型例であり、
DC-016のACL既定DACL回避策が「操作自体は成功するが効果がない」という結果に
終わったのと同種の教訓（Windowsのセキュリティ記述子の組み立てロジックは
ドキュメントの字面だけでは正確に予測できず、実機での確認が必須）を再確認する
結果になった。

## Rejected Alternatives

### AppPath（実行ファイルパス）条件のみを実装し、UserSid条件は見送る (alt-ale-app-id-only)

AppPath条件は子プロセスを生成しない単一プロセスアプリにしか有効に機能せず
（子プロセスは別の実行ファイルパスを持つため同じ条件にマッチしない）、
Claude Codeのような対話的エージェントが将来子プロセスを生成するケースを
恒久的にカバーできない。restricted-account-app-isolation changeが別途進行中
であり、そのアカウントSIDを消費するUserSid条件を設計に含めておく方が
手戻りが少ないと判断し、依存関係はあるが両方を設計に含めた
（実装はAppPathを先行させた）。


### JobObjectManagerのPID列挙をポーリングし子プロセスごとに動的にAppPathフィルターを登録する (alt-dynamic-pid-enumeration)

子プロセスの生成からフィルター登録までの間にその子プロセスが最初の接続を
行ってしまうレース窓が構造的に残ることに加え、ポーリングループの実装・
保守コストが増える。UserSid条件（トークン継承により子プロセスも自動的に
カバーされる）で同じ目的をより単純に達成できるため、動的PID列挙は不採用とした。
