# [DC-012] Tier2のprovisioningフェーズはホスト事前キャッシュのポータブルツールをROマウントし、既定でオフラインとする

## Context

テスト自動化等のTier2ユースケースでは、対象アプリを起動する前に、ゲスト内へ
ツールチェーン（Node.js・ブラウザ等）を用意する「provisioning」フェーズが
必要になる場合がある。Windows Sandboxは公式にカスタムベースイメージや
スナップショットの永続化をサポートしておらず、再起動を要するインストーラも
実行できない制約がある。また、provisioning中のネットワークアクセスの可否は
Tier2の脅威モデル（信頼できないものを隔離実行する）と衝突しうる論点だった。


## Decision

Tier2のprovisioningは、ホスト側で事前に用意・キャッシュしたポータブル
（xcopy展開可能）なツールチェーンを読み取り専用でゲストにマウントし、ゲスト
内ではPATH設定・展開などの軽量な処理に留める。ツールチェーンの取得・バー
ジョン解決自体はsrmの責務とせず、ユーザー側または既存ツール（npm/winget等）
に委ねる。provisioningフェーズのネットワークアクセスは既定でオフラインとし、
許可する場合は明示オプトインの上でDC-011のexecutionフェーズと同じ
`allow_hosts`審査下に置く。


## Rationale

Windows Sandboxは再起動を要するインストーラを実行できず、カスタムベース
イメージも非公式のため、「ゲストの外で用意し、マウントするだけ」にする方式が
現実的な制約に合致する。srmがツールチェーンのバージョン解決・ダウンロードまで
担うのはパッケージマネージャの再実装に近く、DC-005（既存ライブラリの活用を
優先する）と同じ考え方から、srmの責務をマウント・展開の宣言的な実行に限定
する方が保守コストに見合う。provisioning中のネットワークを既定オフラインに
するのは、Tier2の存在理由である「信頼できないものを隔離実行する」ことに対し、
provisioning中の供給網リスク（汚染されたパッケージの取得等）がその境界の
内側で発生することを避けるため。


## Implications

- ポリシーYAMLに`provision:`セクション（toolchain宣言・steps）を追加する 必要がある
- ホスト側に`%ProgramData%\SRM\toolchain-cache\`相当のキャッシュ領域を 新設する必要がある
- provisioningフェーズのネットワーク許可はDC-011の`allow_hosts`機構を そのまま再利用できる見込み

## Rejected Alternatives

### provisioningフェーズは既定でネットワークアクセスを許可 (alt-online-provisioning-default)

利便性は高いが、Tier2が防ごうとしている供給網リスクをprovisioning中に
許してしまうことになり、脅威モデルと矛盾する。


### srmがツールチェーンのバージョン解決・ダウンロードを担うパッケージ マネージャ機能を持つ (alt-srm-package-manager)

実装・保守コストが大きく、npm/winget等の既存エコシステムと機能が重複
する。srmのスコープを超える。


## Review Triggers

- 実運用でオフラインprovisioningの準備コストがユーザーにとって過大だと 判明した場合、オンラインprovisioningを既定寄りに見直す
- Windows Sandboxがカスタムベースイメージ/スナップショットを公式サポート した場合、provisioning方式全体を再検討する
