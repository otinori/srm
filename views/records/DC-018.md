# [DC-018] srm.exe/Srm.Mcp.exe/Srm.PolicyEditor.exeを同一binフォルダへpublishする際のSystem.Text.Json/System.IO.Pipelinesバージョン競合を解消する

## Context

DC-017の実機確認（9.1〜9.7）をWindows実機（Hyper-V/Windows Sandbox有効）で
再開し、`tools\package.ps1`（Release/PR PrereleaseワークフローとGitHub Actionsが
実際に使う手順そのもの）でパッケージした`srm-<version>-dev`一式に対して検証した。

9.1（MCPクライアント経由のCLI相当ツール確認）の途中、`bin\srm.exe list`/
`run`/`stop`がすべて`System.IO.FileNotFoundException: Could not load file or
assembly 'System.IO.Pipelines, Version=10.0.0.0, ...'`で無条件にクラッシュする
ことを発見した（`RunningAppRegistry.Save`/`StructuredLogger.Log`が内部で呼ぶ
`System.Text.Json.JsonSerializer.Serialize`が原因）。`Srm.Cli`単体でpublishした
フォルダでは再現せず、3アプリを同一`bin\`へ結合publishした場合にのみ発生することを
確認した。

根本原因は`tools\package.ps1`のコメントにある前提
「Since all are self-contained deployments of the same .NET 8 runtime/RID,
the shared runtime DLLs are byte-identical」が成立していなかったこと。
`Srm.Mcp.csproj`が参照する`Microsoft.Extensions.Hosting 10.0.9`（ModelContextProtocol
SDKの土台）が、`System.Text.Json`/`System.IO.Pipelines`を10.0.9（.NET 8の
フレームワーク同梱版=8.0.x系とは別系統のNuGetパッケージ版）へ引き上げる。
`Srm.Cli`/`Srm.PolicyEditor`はこれらを直接参照せず、自己完結publish時に
フレームワーク同梱版（deps.jsonに記載なし＝ランタイムパックの一部）を暗黙に使う。
`package.ps1`が3アプリを同一フォルダへ順にpublishすると、後発の`Srm.Mcp`が
同名DLLを10.0.9版で物理的に上書きするが、`srm.deps.json`はこれを関知しない
（Trusted Platform Assembliesに登録されない）ため、`srm.exe`が
`System.Text.Json.dll`（実体は10.0.9版に上書き済み）経由で
`System.IO.Pipelines`を要求した際、ファイルは隣にあるのにdeps.json上は
「存在しないアセンブリ」としてロードに失敗する。

さらに深刻な波及として、Tier2の`srm --nested`（ゲスト内で起動される`srm.exe`
そのもの。`ToolingHostDir`としてMCPサーバー自身の`AppContext.BaseDirectory`＝
同じ壊れた結合`bin\`フォルダがマップされる）も起動直後の最初のログ出力で
同じ例外を出してクラッシュしており、`ready.signal`がタイムアウトするだけで
ホスト側からは「VMの起動が遅い」としか見えない、原因の特定が難しい形で
チャネルA（Tier2）・チャネルB（オートパイロット）を丸ごと機能不全にしていた
（ゲスト側`control\nested.log`で同一のスタックトレースを確認して特定した）。


## Decision

`src\Srm.Runtime\Srm.Runtime.csproj`（`Srm.Cli`/`Srm.Mcp`/`Srm.PolicyEditor`
すべてがProjectReferenceする共通プロジェクト）に、`System.Text.Json`と
`System.IO.Pipelines`を明示的に`Version="10.0.9"`（`Srm.Mcp`が実際に解決している
バージョンと同一）でPackageReferenceとして追加した。これにより3アプリすべてが
NuGet解決の時点で同一バージョンの同一DLLを持つことが保証され、
`package.ps1`が前提としていた「byte-identicalだから上書きしても安全」が
実際に成立するようになる。

`package.ps1`自体（各アプリを別々にpublishしてから同一`bin\`へ結合する方式）は
変更しない。`Srm.Mcp.exe`が`srm.exe`と同じフォルダにいることを前提にした
隣接パス探索（`policies\`自動探索、evidence監視プロセスの起動）が既存設計として
存在するため、フォルダを分離する代替案よりも影響範囲が小さい。


## Rationale

代替案として「各アプリを別サブフォルダへpublichし、`bin\`直下では実行ファイルの
シンボリックリンクやランチャーだけを置く」方式も検討したが、`Srm.Mcp`の
`PolicyPathResolver`/evidence監視プロセス起動ロジックが`AppContext.BaseDirectory`
隣接に`srm.exe`/`policies\`が存在することを前提に実装済み（DC-017実装時点）で
あり、変更範囲・リグレッションリスクが今回のバージョン固定より大きい。

バージョンを固定する対象を`Srm.Runtime`に選んだのは、3アプリ全てが
ProjectReferenceする唯一の共通点であり、ここに1箇所追加するだけで
`Srm.Cli`/`Srm.PolicyEditor`の各csprojを個別に変更せずに済むため。
固定バージョンの値（10.0.9）は「フレームワーク同梱の8.0.x系へ`Srm.Mcp`側を
下げる」のではなく「`Srm.Mcp`が要求する10.0.9へ他2アプリを揃える」方向を
選んだ。ModelContextProtocol SDK（1.4.1）が10.0.9を要求してNuGet解決した
実績があり、逆方向（10.0.9側を8.0.xへ下げられるか）は
ModelContextProtocol/Microsoft.Extensions.Hosting側の互換性次第で不確実
だったため。

この修正はTier2ゲスト内`srm --nested`のクラッシュも同時に解消する
（`ToolingHostDir`が同じ結合`bin\`フォルダを指しているため）。実機で
`srm.exe list/stop`の成功、および`tier2-notepad-test`ポリシーでの
`readySignalTimedOut: false`とnotepad.exeの起動を確認済み（9.1・9.3再検証）。


## Implications

- 今後`Srm.Mcp`が参照するMicrosoft.Extensions.Hosting/ModelContextProtocol SDKを 更新し、System.Text.Json/System.IO.Pipelinesの解決バージョンが変わった場合、 `Srm.Runtime.csproj`の明示バージョンも追随させる必要がある（放置すると このDecisionRecordが解消したのと同じクラッシュが再発する）
- `tools\package.ps1`のコメントにある「shared runtime DLLs are byte-identical」 という前提は、今回のように新しいPackageReferenceが3アプリのいずれかにのみ 追加された場合に再び崩れうる。新規PackageReferenceを追加する際は、 同一binフォルダへ結合される他アプリと解決バージョンが一致しているか `dotnet list package --include-transitive`で確認する運用上の注意が必要
- CIの`windows-latest`ランナーでの`dotnet build`/`dotnet test`はこの種の 「複数自己完結アプリの結合publish」を検証しないため、今回のバグはCIでは 検出できず実機PoCでのみ発見できた（DC-016等と同じ「実機PoC以外では 見つからないクラス」の不具合）

## Review Triggers

- Microsoft.Extensions.Hosting/ModelContextProtocol SDKの更新時、 System.Text.Json/System.IO.Pipelinesの解決バージョンが変わっていないか `dotnet list package --include-transitive`で確認する
- パッケージング結合の脆さ自体（新規PackageReference追加のたびに手動確認が 必要）が繰り返しコストになると判明した場合、各アプリを別サブフォルダへ publishする方式への切り替えを再検討する
