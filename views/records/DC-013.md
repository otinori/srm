# [DC-013] Tier2のoutboxはスキャン結果を自動ゲートにせず、検疫→人間による明示的昇格の二段構えとする

## Context

Tier2の実行結果（AIエージェントの生成物・テストエビデンス、あるいはマルウェア
解析の成果物）はoutbox（RWマップフォルダ、DC-010）経由でホストに渡る。しかし
この用途には相反する2パターンがある——「安全なものを取り出して使いたい」
（AIエージェント/テスト自動化）と、「危険なものそのものを持ち帰りたい」
（マルウェア解析・未知バイナリ調査、DC-002が本来Tier2に想定していた用途）。
スキャン結果をどう扱うか、outboxの内容をいつ・どうやってユーザーの作業ディレ
クトリに反映するかを決める必要があった。


## Decision

outboxの内容は、VM停止確定後（DC-010の`stopped.signal`受信後）にホスト側で
オフライン処理する検疫パイプラインを通す。
1. マニフェスト生成（各ファイルのSHA256/サイズ/相対パスを記録。DC-003のSHA256
   サイドカー方式を踏襲）
2. 構造検査・サニタイズ（パストラバーサル・シンボリックリンク/reparse point・
   予約デバイス名の拒否、クォータ超過分の切り捨て）
3. Windows Defender（`MpCmdRun.exe`）による静的スキャン。結果は合否判定には
   使わず、メタデータとして記録するのみ
4. `%ProgramData%\SRM\evidence\<app>\<runid>\` への検疫保存（ユーザーの作業
   ディレクトリには一切触れない）
5. 新規CLIコマンド（`srm evidence list/show/promote/reject`）による人間の
   明示操作でのみ、検疫からユーザー指定先へのコピーを行う（move ではなく
   copy。検疫側の控えを監査証跡として残す）
実行中のクォータ超過対策として、ホスト側でFileSystemWatcher相当のポーリング
監視スレッドを走らせ、閾値超過時は`stop.signal`相当で早期終了させる。検疫
データは`logging.retention_days`と同様の考え方で保持期限（既定7日、ポリシー
で上書き可）を設ける。


## Rationale

AIエージェント/テスト自動化用途とマルウェア解析用途とでは「スキャンに引っか
かる」ことの意味が正反対（前者では異常、後者では想定通りの成果物）なので、
スキャン結果を自動的な受け入れ/拒否のゲートにすると、どちらかの用途で誤動作
する。両立させるには、スキャン結果をラベルとして記録するだけに留め、実際に
取り出すかどうかは常に人間が判断する構造にするのが妥当。これはDC-004の
「AI生成物は無審査で適用しない」という既存原則を、ポリシーではなく実行成果物
にも適用した形になる。promoteをcopyにするのは、昇格後に問題が発覚した場合の
監査証跡を残すため。


## Implications

- ポリシーYAMLに`evidence.retention_days`のようなフィールドを追加する必要が ある
- 新規CLIコマンド`srm evidence list/show/promote/reject`の実装が必要
- 検疫ストア`%ProgramData%\SRM\evidence\<app>\<runid>\`のACL設計（管理者/ 実行ユーザーのみアクセス可、等）が別途必要
- ログイベントに`evidence_quarantined`/`evidence_promoted`/`evidence_rejected` を追加する必要がある（spec-v01-srm-runのログ設計拡張）

## Rejected Alternatives

### スキャン結果に基づいて自動的にoutboxの内容を作業ディレクトリへ反映/拒否する (alt-auto-gate)

マルウェア解析用途では「スキャンで検出される」ことが正常な成果物であり、
自動拒否すると本来欲しかった証跡を消してしまう。逆にAIエージェント用途
では自動的に作業ディレクトリへ混ぜてしまうと、DC-004で確立した「AI生成物
は無審査で適用しない」という原則に反する。


### promoteをコピーではなく移動にする (alt-move-on-promote)

一度昇格すると検疫側の控えが消え、後から問題が発覚した際の監査証跡が
失われる。ディスク消費は増えるが安全側に倒す。


### NTFSクォータ/FSRM（File Server Resource Manager）でクォータを強制する (alt-fsrm-quota)

追加のWindows機能有効化が必要で導入コストが高い。ホスト側の監視スレッド
（ポーリング）の方が依存が少なく現実的な第一手。将来の最適化候補として
残す。


## Review Triggers

- ホスト側ポーリング監視の性能/精度がPoCで不十分と判明した場合、FSRM/NTFS クォータ方式へ切り替えを検討する
- 実運用でcopy方式によるディスク消費が問題になった場合、move+ハッシュ記録 のみ保持等の軽量化を検討する
