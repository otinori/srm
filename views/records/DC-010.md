# [DC-010] Tier2実行アーキテクチャ：Windows Sandbox内にAppContainerを重ねる多層防御とし、ゲスト内エージェントは新規開発しない

## Context

Tier2（Windows Sandbox）の実行基盤はDC-002で「VMベースの強力な分離」と方針決定
されたのみで、具体的な実行の仕組みは未設計だった。RunCommand.csは現状policy.Tier
を見ておらず、常にAppContainerLauncherを使う実装しか存在しない
（WindowsEditionDetector.ThrowIfTier2OnHomeによるHomeエディションのガードのみ
実在する）。Windows Sandboxはセッション終了後にゲスト環境を完全に破棄する特性を
持つ一方、ゲストは毎回まっさらなWindowsから起動するため、対象アプリをゲスト内で
どう安全に起動し、VM単体よりも隔離を強化するかを決める必要があった。


## Decision

Tier2はWindows Sandbox（VM境界）の内側にTier1のAppContainer隔離を重ねる多層防御
構成を採用する。ゲスト内で対象アプリを起動する処理は新規のゲストエージェントを
開発せず、srm.exe自身をLogonCommandから「ネストモード」（例: `srm.exe run <policy>
--nested`）で起動し、既存の`AppContainerLauncher`/`JobObjectManager`をゲスト内で
そのまま再利用する。AppContainer SIDは`DeriveAppContainerSidFromAppContainerName`
がマシン非依存の決定的関数（名前のSHA256から導出）であることを利用し、ホスト側で
VM起動前に事前計算・対象フォルダへのACL事前付与を行う。これによりゲスト内での
ACL設定ステップを省略する。host↔guest間のライフサイクル制御（起動完了通知・停止
シグナル）は、マップフォルダ配下の`control/`フォルダに置く合図ファイル
（`ready.signal` / `stop.signal` / `stopped.signal`）でやり取りする。


## Rationale

VM境界だけの隔離だと、ゲスト内で対象アプリが取れる権限がゲストの管理者権限その
ものになり、Tier1で培った最小権限の思想が活かされない。AppContainerを内側に重ね
ることで、VMエスケープとAppContainer突破の両方が必要という多層防御になる。ゲスト
内エージェントを新規開発する代わりにsrm.exe自身を再利用するのは、DC-002の「同一
ポリシーエンジンを使い、ユーザー体験を統一する」という思想の延長であり、実装・
保守コストの二重化を避けられる。AppContainer SIDの事前計算・ACL事前付与は、ゲスト
起動のたびに発生していたはずのセットアップコストを削減し、「クリーンに壊す」と
いう価値を損なわずに起動オーバーヘッドを抑える。


## Implications

- RunCommand.cs にTier2向けの分岐（.wsb生成・WindowsSandbox.exe起動・ ネストモード呼び出し）を実装する必要がある
- srm.exe に `--nested` 相当の内部モードを追加し、ホスト専用ステップ （WFP登録・ホスト側レジストリ登録等）をスキップする分岐が必要
- AclManager をホスト側で「VM起動前にマップフォルダ元のホストパスへ事前付与」 できるよう呼び出しタイミングを変更する必要がある
- RunningAppRegistry はTier2の場合、ゲスト内PIDの代わりにVMを表すホスト側の ハンドル（コンテナプロセス）を保持する形に拡張する必要がある

## Rejected Alternatives

### VM境界のみで隔離（AppContainerを併用しない） (alt-vm-only)

ゲスト内の対象アプリがゲストの管理者権限を持ってしまい、Tier1で確立した
最小権限の原則から後退する。Tier2が高リスク実行（未知バイナリ・マルウェア
解析等）を想定している以上、単一境界では防御として不十分。


### ゲスト内エージェントを新規にゼロから実装 (alt-new-guest-agent)

Tier1の`AppContainerLauncher`/`JobObjectManager`と機能的にほぼ同じものを
別実装することになり、二重の実装・保守コストが発生する。srm.exe自身を
ネストモードで動かす方が既存資産を最大限再利用できる。


## Review Triggers

- PoCで「ホストが事前付与したACLがマップフォルダ経由でゲストに正しく反映 されない」と判明した場合、ゲスト内での再付与方式に戻す
- srm.exeのネストモードがLogonCommand経由で安定して起動しないと判明した場合、 専用の軽量ブートストラップの実装を再検討する
