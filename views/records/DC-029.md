# [DC-029] claude-code 2.1.233での再検証でDC-016のAppContainerビジーループが再現しないことを確認（DC-016をSupersede）

## Context

DC-016は、claude-code CLI（Bunランタイム、v2.1.197時点）をAppContainer内で
`-p`実行すると、対象プロセスがカーネルモードCPUを消費し続けるビジーループに
陥る未解決バグを記録していた。根本原因は「AppContainerの既定DACLにALL
APPLICATION PACKAGESが含まれないため、Bunが起動時に作成する名前付きパイプ
への`NtCreateNamedPipeFile`が失敗し続け、claude-code側がこの失敗を無限
リトライしてしまう」という仮説まで到達していたが、確定はしなかった。
DC-016自身が「claude-codeがどの機能でいつ名前付きパイプを開こうとするかは
非公開コードのため特定できない」と記しつつ、「セッション再開・シングル
インスタンス確認・MCP関連の待受」を候補として挙げていた。

本レコード作成のきっかけは、ユーザーとの会話で「同一マシン上で動く複数の
Claudeインスタンス間の通信（クロスセッションメッセージング機能）を名前付き
パイプで実装しようとしていたのではないか」という仮説が提示されたこと。
この仮説自体は本レコードでは検証できていないが、それとは独立に「そもそも
現在インストールされているclaude-code（2.1.233、DC-016調査時のv2.1.197
より新しい）で同じ再現手順を試すとどうなるか」を実機で確認した。

## Decision

DC-016と同一の再現手順（`policies/claude-code.yaml`に`arguments: -p
"Reply with exactly: PONG" --output-format text`を追加しただけの一時
ポリシー、`%TEMP%\srm-dc016\claude-code-repro.yaml`）を、実機
（管理者PowerShell、`srm run <一時ポリシー> --no-integrity-check`）で
再実行した。

対象プロセス（`claude.exe -p "Reply with exactly: PONG" --output-format
text`、AppContainerでサンドボックス化）のCPU使用時間を10秒間隔で2回計測
したところ、6.890625秒のまま**まったく増加しなかった**（DC-016では
経過時間とほぼ1:1でCPU時間が増え続けるビジーループが特徴だった）。
`Responding`は`True`のままで、その後さらに5秒待つとプロセスは正常に
終了した。DC-016のビジーループ症状は**再現しなかった**。さらに、
`srm run`を実行したコンソール（対象プロセスがコンソールを継承する設計、
resource-access-audit-logging DC-028参照）に、想定通り`PONG`が出力
されたことも確認した（サンドボックス化された状態でclaude-codeが
正常にAPI呼び出し・応答出力まで完了したことの直接的な証拠）。

以上により、DC-016の状態を「Draft/Published」から「Superseded」へ変更し、
本レコードで置き換える。

## Rationale

再現しなかったこと自体は前向きな結果だが、根本原因（DC-016で確定できな
かった「なぜBun/claude-codeが名前付きパイプの失敗を無限リトライして
いたか」）が実際に修正されたのか、それとも別の要因（Windows Update・
Bunランタイムのバージョン変更・claude-code側のIPC実装変更等）で症状が
たまたま出なくなっただけなのかは、今回の再検証だけでは判別できない。
再現しなかったためCPUスパイクが無く、`srm diag --stacktrace`で
以前と同じ関数（`NtQueryInformationToken`等）が今も出ないかを比較する
機会も得られなかった（採取対象のCPU消費が無いため意味のあるサンプルが
取れない）。

ユーザーが提示した「クロスセッションメッセージング機能の名前付きパイプ
実装」という仮説についても、それが本当にDC-016の原因だったのか、
その後の実装変更で解消されたのかは、claude-code自身の非公開コードを
見られない以上確認できない。本レコードは「現在のバージョンでは再現しない」
という実機での事実のみを記録し、原因の特定はしない。
