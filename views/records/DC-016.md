【2026-07-13 Bunのオープンソースコードから名前付きパイプの正体を特定】
claude.exe（Bunでコンパイル）のBun本体は`github.com/oven-sh/bun`で
公開されている。ソース内を`CreateNamedPipe`/`NamedPipe`で検索したところ、
`src/runtime/socket/WindowsNamedPipe.rs`・`WindowsNamedPipeContext.rs`・
`Listener.rs`が見つかった。これらから、BunのネットワークAPI
（`net.Server.listen()`相当）は、Unixドメインソケット風のパス
（ファイルシステムパス）を`.listen()`に渡された場合、Windows上では
それを名前付きパイプとして扱う汎用実装になっていることが判明した
（`Listener.rs`の`normalize_pipe_name`/`is_named_pipe`判定）。libuvの
`uv::Pipe`をラップし、TCP/Unixソケットと同じイベントループ・ハンドラで
扱う設計（µWebSockets/uSocketsとの橋渡し）。

一方、`ipc_host.rs`は`Bun.spawn()`/`process.send()`（子プロセスとの
IPCチャンネル）のJSホスト実装で、Windows上でも同じ名前付きパイプ機構を
経由すると推測される。ただし本レコードの再現手順（`claude -p "..."`単体
実行）は明示的な子プロセスspawnを伴わないため、`ipc_host.rs`経由という
よりは、claude-code自身が起動時に何らかのローカル制御用ソケット
（セッション再開・シングルインスタンス確認・MCP関連の待受等）を
Unixソケット/名前付きパイプで開こうとしている可能性が高いと考えられる。
ただし、この「claude-codeがどの機能でいつ`.listen()`を呼ぶか」という
部分はBunランタイム自体ではなくAnthropic製claude-code自身のアプリ
ケーションコード（バイナリにバンドルされた非公開のJS/TS）の中にあり、
Bunのオープンソースリポジトリを見るだけではこれ以上特定できない
（Bunが提供しているのは「名前付きパイプをソケットとして扱える」という
下層の汎用機構だけで、いつ・なぜそれを呼ぶかはclaude-code側の判断）。

Web検索で、Microsoft公式ドキュメント（Named Pipe Security and Access
Rights）が「AppContainerで動くパッケージアプリケーションが名前付き
パイプに接続するには、既定のセキュリティ記述子には含まれない
ALL APPLICATION PACKAGESグループがDACLに必要」という趣旨を明記している
ことを確認した。名前付きパイプの既定のセキュリティ記述子は
LocalSystem・Administrators・作成者所有者に完全アクセス、Everyone/匿名
に読み取りアクセスを与えるのみで、AppContainerパッケージSIDは含まれない。
Bun側のコードはAppContainer環境を想定した特別なセキュリティ記述子を
一切設定していない（通常のNode.js/Bunアプリケーションはこのような環境で
動くことを想定していないため）。

これらを総合すると、最も筋の通る説明は次の通りである: claude-code
（Bunランタイム上）が起動時にローカルの名前付きパイプ（Unixソケット風の
パス）を開こうとする → AppContainerトークンでは既定のDACLにより
`NtCreateNamedPipeFile`の内部アクセスチェック
（`SeAccessCheckWithHintWithAdminlessChecks`）が失敗する → Bunまたは
claude-code側のエラーハンドリングがこの失敗を握りつぶし（またはtransient
なエラーと誤認し）、成功するまで即座に再試行し続ける → 結果として
観測されたビジーループになる。根本原因の「なぜ失敗するか」はWindowsの
文書化された既知の挙動でほぼ説明がつくが、「なぜBun/claude-codeが
この失敗で無限リトライしてしまうか」（本来はエラーとして表面化すべき
設計不備）は、claude-code自身の非公開コードの中にあり、外部からは
これ以上追えない。

【2026-07-13 複数インスタンス間の固定名パイプ競合仮説を検証（否定的結果）】
ユーザーから新しい仮説が提示された: 直前のFileIOイベント調査時、マシン上に
複数のclaude.exeプロセスが同時に動いていたことが分かっていた。もし名前付き
パイプの名前が固定（プロセス固有でない）で複数のclaude-codeインスタンス間の
調整用だとすると、サンドボックス化インスタンスが「他の既存インスタンスが
作った、AppContainerのSIDを含まないパイプ」に接続しようとして永久に失敗して
いる可能性がある、というもの。これなら「サンドボックス外の通常のclaude-code
同士なら普通に繋がるので誰も気づいていない」ことの説明にもなる。

検証のため、ユーザーはこの仮説を確実に検証できるようOSを再起動してclaude.exe
プロセスを一旦すべて終了させ、本レコード用のセッション1つ（claude.exeが
`claude rc`として起動する親プロセスと、`--print --sdk-url ...`で実際の
セッション処理を行う子プロセスの2プロセス構成であることが`Get-CimInstance
Win32_Process`で判明。例: 親PID 8372→子PID 7100）だけが動く状態を作った。

1. まず`[System.IO.Directory]::GetFiles('\\.\pipe\')`で現在の名前付き
   パイプ一覧を確認したところ、`\\.\pipe\uv\0-8372`・`\\.\pipe\uv\1-8372`・
   `\\.\pipe\uv\18446744073709551615-8372`・
   `\\.\pipe\uv\18446744073709551615-7100`が見つかった。`uv\`はlibuv
   （Bunがラップしている）のWindows上での匿名パイプ実装の命名規則で、
   パイプ名にプロセス自身のPIDが埋め込まれている（＝プロセス間で共有される
   固定名ではない）ことが分かった。

2. 同じ再現手順（`-p "Reply with exactly: PONG" --output-format text`、
   `--no-integrity-check`で一時ポリシーとして起動）を実行し、サンドボックス
   化された`claude.exe`（PID 12864）がビジーループすることを再確認した
   （5秒間でCPU時間も5秒増加、コア1つ分をほぼ専有）。`Get-CimInstance
   Win32_Process`で子プロセスの有無を確認したところ、PID 12864に紐づく
   子プロセスは一切存在しなかった（親はsrm.exe自身のPID 1116のみ）。これは
   「親子間の標準入出力パイプが待受で詰まっている」という仮説（非隔離
   セッションの8372→7100のパターンから連想されたもの）を直接否定する
   結果である。`-p`（ヘッドレス印字モード）はインタラクティブな
   `claude rc`とは別のコードパスで、子プロセスをspawnしない単一プロセス
   完結型であることが分かった。

3. ビジーループ中に再度パイプ一覧を確認したが、PID 12864に関連する新規
   パイプは一切出現しなかった（既存の8372/7100のuvパイプのみ）。これは
   DC-016で既に確立していた「`NtCreateNamedPipeFile`がオブジェクトマネージャの
   セキュリティチェック段階で毎回失敗しており、パイプが一度もパイプ
   名前空間に公開（publish）されない」という理解と整合する結果であり、
   この方法では「固定名か否か」を直接見分けることはできなかった。

4. 決め手となる追加実験として、このセッション（8372/7100）とは別に、
   非サンドボックスの`claude.exe -p "Reply with exactly: PONG"
   --output-format text`をもう一つ`System.Diagnostics.Process`から直接
   起動し、50ms間隔で名前付きパイプ一覧をポーリングして新規出現パイプを
   すべて記録した。結果、このたった1回の正常終了する呼び出し（PID 10092、
   最終的に13.4秒で`PONG`を出力し終了コード0）だけで、`\\.\pipe\uv\
   0-10092`から`\\.\pipe\uv\23-10092`まで**24個**もの自PID紐づきパイプが
   連番で次々と作成されていた。固定名・共有名のパイプは一切登場せず、

したところ、この回避策を適用した状態でも症状は一切変化せず、20秒以上に渡って

組み立てではそもそも参照されていない」ことを強く示唆する結果である。

最も妥当な解釈は次の通り: DC-016で確認済みのMicrosoft公式ドキュメントの
「名前付きパイプの既定のセキュリティ記述子はLocalSystem・Administrators・
作成者所有者・Everyone/匿名読み取りのみ」という記述は、作成元プロセスの
トークンから導出される値ではなく、NPFS（Named Pipe File System）ドライバー
または`\Device\NamedPipe`名前空間ルート側が持つ、継承可能な固定のデフォルトSD
である可能性が高い。Windowsのセキュリティ記述子継承ルールでは、親オブジェクトに
継承可能なACEが既に存在する場合、そちらが優先され、作成元トークンの既定DACLは
参照されない。この回避策が全く効かなかったという実機での否定的結果は、この
解釈と整合する。

この解釈が正しい場合、`srm`（対象プロセスのトークン設定）側からこの問題を
解消する手段は事実上存在しない。残る選択肢はシステム全体の
`\Device\NamedPipe`名前空間ルートのACLを書き換えること（マシン上の全アプリの
全名前付きパイプに影響する、1アプリのサンドボックスのためには不釣り合いに
大きなセキュリティ変更のため強く非推奨）か、windbg等で実際に使われている
セキュリティ記述子の生成元を直接観測することのみ。この回避策のソース変更
（`AppContainerLauncher`のCREATE_SUSPENDED化・既定DACL書き換え）は効果が
無かったため`git checkout`で元に戻した。
