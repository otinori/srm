## Context

SRMはAIネイティブ開発のハーネスエンジニアリングの一部として使うことを想定している。
常時起動し続けるサービスではなく、AIエージェント（Claude Code等）が人間の都度確認を
挟まずに設計書などの成果物を安全かつ高速に作成したり、環境を壊さずにテストを自動化
したりする用途で使う。現状SRMはCLI（srm.exe run/stop/list/logs/validate/evidence）
としてのみ操作可能で、AIエージェントはシェル経由でCLIを呼ぶしかなく、GUIアプリの
状態取得・操作（キー/マウス入力、起動状態確認等）を構造化してAIに渡す手段がない。

MCPサーバーとしてSRMの機能を公開する方式を検討した。SRMは既存方針として常駐デーモン
を持たない（DC-008）。Tier1（AppContainer）とTier2（Windows Sandbox）ではホスト
プロセスとサンドボックス内プロセスの到達可能性（同一デスクトップか別VMか）が根本的に
異なるため、単一の入力注入方式では両Tierをカバーできない。

検討の過程で、Tier2向けに「control/配下にコマンドをファイルとして積むキュー」を
当初案としたが、AIによる長時間の対話的操作を想定すると、対応するcommand/result
ファイルが際限なく積み上がり、かつ`%ProgramData%\SRM\run\<app>\<runId>\`自体に
保持期限の仕組みがそもそも存在しない（ログやevidenceにはretention_daysがあるが
run/ディレクトリ全体には無い）という既存の穴を悪化させることが分かった。また
「いつどんな形で通信できなくなるか分からない以上、単一のチャネルに絞り込む必要は
ない」という運用上の要求もあり、目的の異なる複数チャネルを併存させる方針に落ち着いた。


## Decision

1. MCPサーバーは新規常駐サービスとしては実装せず、MCPクライアント（Claude Code等）が
   stdio経由で都度起動・終了する薄いプロセス（新規`Srm.Mcp`プロジェクト。既存の
   `Srm.Runtime`/`Srm.PolicyEngine`をライブラリとして参照する）として実装する。
   DC-008の「IPC・デーモンなし」方針をMCPサーバー自体にも適用する。

2. 既存CLI相当の操作（run/stop/list/logs/validate/evidence）は、CLIをサブプロセス
   として起動して叩くのではなく、`RuntimeManager`等の既存クラスをMCPツールから直接
   呼び出す形でラップする。

3. GUI操作は目的別に3つのチャネルを併存させる。

   **チャネルA（対話的ライブ制御）** — `send_key`/`send_mouse`/`screenshot`。
   AIが「操作→結果を見る→次を決める」を繰り返す探索的操作向け。
   - Tier1: ホストと同一セッション上で動くAppContainer化プロセス自身のウィンドウ
     ハンドルを特定し、`SendInput`で直接注入する。ブリッジ不要
   - Tier2: 別VMのため対象アプリのウィンドウに直接は届かない。代わりに、
     `WindowsSandbox.exe`がホスト上に開く、ゲストデスクトップをRDPベースで
     レンダリングするウィンドウ自体を対象にする。ホスト側MCPサーバーがそのウィンドウ
     へ`SendInput`すると、既存のRDP転送機構がそのままゲストへ届ける。ゲスト内
     `--nested`側の変更は不要
   - 両Tierとも、送信のたびに対象ウィンドウの実体を再検証し、一致しなければ発行しない
     fail-closedのガードを必須とする（decision 4参照）

   **チャネルB（オートパイロット、Tier2専用）** — 既存`SandboxControlChannel`
   （`control/`配下のシグナルファイルによるhost↔guest同期、DC-010）を、個々の
   キー操作を都度やり取りするコマンドキューとしてではなく、**テストシナリオ
   （手順の並び）をまとめて1回投入し、ゲスト内`--nested`が自律的に最後まで実行して
   結果を返す**方式に拡張する。
   - `control/scenario.json`（host→guest、既存の`policy.yaml`同様「起動前に一度だけ
     配置」パターンを踏襲）
   - `control/scenario-result.json`（guest→host、シナリオ完了時に一度だけ書く）
   - ゲスト内`--nested`と対象アプリは同一セッション上で動くため、ゲスト側の各ステップ
     実行はTier1と全く同じ「同一セッション内`SendInput`＋Job Object PIDスコープの
     ガード」ロジックを再利用できる（新規のウィンドウ解決トリックは不要）
   - 各ステップのスクリーンショット等の証跡は新規の保持期限機構を作らず、既存の
     evidence検疫パイプライン（DC-013、`outbox`→quarantine、`retention_days`）に
     そのまま流す
   - host↔guest間の常時ラウンドトリップが不要なため、通信が不安定でも投入後は
     自律的に完走できる

   **チャネルC（将来オプション、Tier2専用）** — Hyper-V Sockets（AF_HYPERV）を、
   入力操作ではなく**ファイル転送・サンドボックス内プロセスのリアルタイム
   モニタリング**という別カテゴリの機能のために温存する。ゲスト内から任意の
   サービスGUIDを開けるか等、実現可否が未検証のためPoC次第とし、本changeの実装
   スコープには含めない（review_trigger参照）。実現しない場合もチャネルA/Bの設計
   には影響しない。

4. チャネルA（ウィンドウ経由の入力注入）は、送信直前に毎回以下を再検証し、
   いずれか1つでも失敗したら**発行せず中断する**（fail-closed。キャッシュした
   ハンドルを信頼しない。HWNDはOSに再利用されるため）。
   - 対象ウィンドウの所有PIDが、この`runId`に紐づく起動時記録済みプロセス
     （Tier1: Job Object配下PID集合、Tier2: `SandboxLauncher`が起動したプロセス）に
     属していること
   - 所有PIDの実行ファイルパスが期待するバイナリ（Tier2は
     `%SystemRoot%\System32\WindowsSandbox*.exe`）と一致すること
   - ウィンドウクラス名が期待値と一致すること
   - マウス操作の場合、変換後のホスト座標が対象ウィンドウの現在のクライアント領域内に
     収まっていること
   - 送信直前に`SetForegroundWindow`し、実際に対象ウィンドウがフォアグラウンドに
     なったことを確認できること
   - 拒否した場合は`StructuredLogger`に`guard_rejected`イベントとして理由とともに
     記録する

5. MCPツールが操作できる対象は、SRMが起動・管理しているポリシー配下のプロセス/
   ウィンドウに限定する。汎用リモートデスクトップ操作（任意のウィンドウ操作）は
   スコープ外とする。


## Rationale

stdio起動の薄いMCPサーバーはMCPクライアントのライフサイクルに従属するため、デーモンの
インストール・自動起動・クラッシュ復旧という複雑性を持ち込まずに済み、DC-008の思想と
両立する。

チャネルAはTier2でもゲスト内エージェントの変更を一切必要としない。ホスト側の
`WindowsSandbox.exe`ウィンドウは元々RDPでゲスト入力を転送する仕組みを持っており、
それを流用するだけで済むため、新規のホスト↔ゲストプロトコル設計自体が不要になる。
これはDC-010の「ゲスト内エージェントを新規開発しない」という思想の最も強い形での
踏襲である。

チャネルBはコマンド単位ではなくシナリオ単位でファイルをやり取りすることで、
「ファイルが際限なく積み上がる」問題を構造的に解消する（1run＝シナリオ1個＋結果1個）。
証跡をevidence検疫パイプラインに委譲することで、新規の保持期限ロジックを実装せずに
済む。また常時ラウンドトリップに依存しないため、「AIによるテスト自動化」という
ハーネス用途において、接続の一時的な不調があっても投入済みシナリオは完走できる
（「いつコントロールできなくなるか分からない」という運用要求に対応）。

チャネルCをファイル転送・モニタリング専用として切り離すことで、実現可否が
Windows実機PoC待ちであっても、チャネルA/Bの設計・実装は先行して進められる。
制御（操作）とオブザーバビリティ（監視）を別カテゴリの機能として最初から分離して
おくことで、将来HvSocketが使えないと判明しても後戻りが発生しない。

複数チャネルを併存させる方針自体は、単一障害点（1つの通信方式が使えなくなると
AIによる制御が完全に止まる）を避けたいという要求に基づく。目的の異なるチャネルを
重ねることで、DC-010以来「ファイルベースのポーリングは単純で壊れにくい」という
設計原則を保ちながら、対話的操作という新しい要求にも応えられる。

操作対象をSRM管理下のプロセス/ウィンドウに限定し、かつ毎回実体を再検証する
fail-closedガードを必須にすることで、「隔離しつつ操作したい」という要求と
「外部からの干渉を遮断する」というSRM本来の隔離目的との緊張を、実装レベルで
具体的に制御する。特にチャネルAはホスト側のウィンドウに`SendInput`するという
性質上、対象を取り違えるとサンドボックス外（ホストの他のウィンドウ）に誤って
入力が漏れるリスクがあるため、このガードは他のどの実装判断よりも優先度が高い。


## Implications

- 新規`Srm.Mcp`プロジェクトが必要（MCP C# SDKに依存、stdio transport）
- チャネルA: ウィンドウ実体の再検証ロジック（所有プロセスの実行ファイルパス・ ウィンドウクラス名・クライアント領域バウンディングチェック・フォアグラウンド 確認）をTier1/Tier2共通の再利用可能なコンポーネントとして実装する必要がある
- チャネルB: `SandboxControlChannel`に`scenario.json`/`scenario-result.json`の 読み書きを追加し、`--nested`のメインループにシナリオ実行ディスパッチを 組み込む必要がある。ゲスト内のステップ実行はTier1と同じSendInput+Job Object ガードのロジックを再利用する設計にする
- シナリオの証跡（スクリーンショット等）をevidence検疫パイプラインに統合する ための`outbox`書き込み規約を決める必要がある
- MCPツールのスキーマ設計（run/stop/list/logs/validate/evidence + send_key/ send_mouse/screenshot + run_scenario/get_scenario_result）が必要
- 入力注入・画面キャプチャ・ガード拒否という新しい操作カテゴリの監査ログを `StructuredLogger`の既存JSON Linesログに統合する必要がある
- チャネルCは本changeの実装スコープ外。実装するかどうかは別途PoC結果を見て 判断する（review_trigger参照）

## Rejected Alternatives

### MCPサーバーを常駐サービス化する (alt-daemon-mcp)

常時起動を前提とするとDC-008の「IPC・デーモンなし」方針から逸脱し、SRMが
「常時起動し続けるものではない」ハーネス用途を想定している利用シーンにも反する。
インストール・自動起動・クラッシュ復旧の複雑性が増す。


### Tier2の対話的操作をcontrol/配下の1コマンド1ファイルのキューで実装する (alt-percommand-file-queue)

AIによる長時間の対話的操作を想定すると、command/resultファイルが際限なく
積み上がる。`run/`ディレクトリ自体に保持期限の仕組みが元々存在しない
（ログ・evidenceにはretention_daysがあるがrun/には無い）ため、この問題を
悪化させる。ウィンドウ経由のチャネルAで対話的操作は代替でき、ゲスト内変更も
不要になるためこちらを採らない。オートパイロット用途（チャネルB）では
「シナリオ単位」に粒度を変えることで同じ問題を回避する。


### Tier2の入力操作そのものをnamed pipe/socketのライブブローカーで実装する (alt-live-ipc-control)

DC-010〜DC-015の過程で、VM境界をまたぐ通信はHyper-V Firewall等が期待通りに
機能しないなど技術的に不安定であることが実機PoCで判明済み（DC-015参照）。
また常駐のゲスト内リスナーが必要になりDC-008から逸脱する。入力操作という
制御パスに関しては採用せず、チャネルA（ウィンドウ経由）とチャネルB
（ファイルベースのシナリオ投入）で代替する。ライブソケット自体（HvSocket）は
制御目的ではなくファイル転送・モニタリング目的のチャネルCとして温存し、
検討自体は打ち切らない。


### 任意のウィンドウを操作できる汎用リモートデスクトップ機能として実装する (alt-generic-remote-desktop)

SRMのスコープを「ポリシーで管理する対象アプリの操作」に限定しないと、隔離目的
との矛盾が拡大し、悪用時の被害範囲（任意プロセスへの入力注入）も無制限に広がる。


### Windows 11 24H2で追加された公式`wsb.exe` CLI（`wsb start`/`connect`/`exec`/ `share`/`stop`）を基盤にチャネルA/Bを構築する (alt-wsb-cli)

調査の結果、`wsb connect`が開くRDPウィンドウはチャネルAが元々狙っていた対象と
一致し、`wsb exec`（要`connect`済みの対話セッション、標準出力の取得手段なし）を
使えばチャネルBの自作`scenario.json`ポーリング・LogonCommandブートストラップを
相当簡略化できる可能性が高い。実際にこの方式でWindows SandboxをMCP化した先行
実装（`yourtablecloth/WindowsSandboxMcp`、experimental）も存在し、技術的な
筋の良さは確認できた。

不採用・保留の理由は「Windows 10互換性を守りたいから」ではない。Windows 10は
既にサポート終了しており、本来SRMが正式にターゲットすべき対象ではない
（現行READMEの「Windows 10 / 11 Pro または Enterprise」という記載自体が実態と
ずれている可能性があり、別途見直しの余地がある）。

保留の実際の理由は、開発者（otinori）が現時点でWindows 11実機を一切保有して
おらず、`wsb` CLI（24H2限定）はおろかWindows 11自体の実機検証ができない、
という一時的・偶発的な制約による。SRMはDC-010以降、Windows固有コードは実機
PoCで裏付けてから設計を確定する（DC-011→DC-015の改訂、Home版Tier2ガードの
扱い等）という実践を一貫してとってきており、検証手段のない経路を主要設計として
採用することは同じリスクを繰り返すことになる。技術的な筋は良く、むしろ
Windows 11（24H2）が本来の主要ターゲットであることを踏まえると`wsb` CLIの方が
将来の第一候補になりうるため不採用ではなく保留とし、Windows 11実機（24H2で
あれば`wsb` CLI採用、それ未満でも最低限の実機検証は可能）が確保でき次第、
改めて採用可否・優先度を判断する（review_trigger参照）。現行のファイル/
ウィンドウベースのチャネルA/Bを選ぶ理由も同様に「今手元にある環境（Windows 10）
で検証できるから」という実務上の理由であり、Windows 10を恒久的なターゲットと
見なしているわけではない。
