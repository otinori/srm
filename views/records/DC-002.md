## Context

アプリケーションの隔離実行基盤を選定する必要があった。
「軽量で常用できる」実行基盤と「強力だが重い」実行基盤の両方のニーズがあり、
リスクレベルに応じて使い分けたい。


## Decision

同一のポリシーエンジンを使い、リスクレベルに応じて実行基盤を切り替える二段構えを採用する。
- Tier 1: AppContainer — 軽量・高速・OS内サンドボックス（通常実行・全Windowsエディション対応）
- Tier 2: Windows Sandbox — VM ベース・強力な分離（高リスク実行・Pro以上が必要）
ポリシーYAMLの `tier` フィールドで切り替える。HomeエディションでTier2を指定した場合はエラー終了。


## Rationale

AppContainerは軽量で起動が速く日常的なゲーム・開発ツール実行に適する。
Windows Sandboxは強力だがPro以上限定・起動が遅いため高リスク用途に限定する。
同一ポリシーエンジンを共有することでユーザー体験を統一し、学習コストを下げる。


## Implications

- Tier 2はWindows Pro以上が必要——HomeユーザーへはTier 1のみを推奨
- AppContainerでのOpenGL/DirectX動作はPoC検証が必要（技術リスク）
- WFPによるAppContainer SIDベースフィルタリングの実現可否もPoC要確認

## Rejected Alternatives

### AppContainerのみ（単一Tier） (alt-single-tier)

未知のバイナリやマルウェア解析など高リスク実行を安全に扱えない。
将来のユースケース（セキュリティテスト等）に対応できず柔軟性が不足する。


### Docker / WSL2 (alt-docker)

DockerはLinuxコンテナベースでWindows固有のAPIアクセス（DirectX等）が困難。
WSL2はゲームや一部のWindowsアプリに対応できない。
WindowsネイティブAPIとの親和性でAppContainer+Windows Sandboxが優れる。


## Review Triggers

- PoCでAppContainer内のGPUアクセスが不可能と判明した場合
- Windows Sandbox APIに破壊的変更があった場合
