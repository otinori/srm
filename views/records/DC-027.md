# [DC-027] srm diag --stacktraceをTier2へ拡張し、実機でTier1比べ著しく遅いETWセッション特性を発見

## Context

DC-020/DC-021で実装した`srm diag --stacktrace`（ETWカーネルCPUスタック
サンプリング、`Srm.Diagnostics.Kernel.KernelCpuStackSampler`）は、Tier1のみ
対応で、Tier2は「対象プロセスが別VM上のカーネルで動くためホストからのETW
セッションでは採取できない」という理由で明示的に非対応のままDC-021の
review_triggerに持ち越されていた。本レコードは、tier2-channel-c-mapped-folder
で追加した汎用request/resultプリミティブ（DC-025）を使ってこのギャップを
解消した実装・実機検証の結果を記録する。


## Decision

ETWセッションはサンプリング対象と同じカーネル上でしか動かせないため、
ホストから直接開始することはできない。ゲスト内`--nested`自身が
`KernelCpuStackSampler`（Tier1と全く同じ実装、`Srm.Diagnostics.Kernel`）を
呼び出して採取し、`kind="stacktrace"`のrequest/resultペア
（`SandboxControlChannel`の汎用プリミティブ、DC-025）でホストとやり取りする
設計にした。診断チャネル（`HandleDiagRequest`）と同じく、採取中は
`BlockUntilStop`ループを同期的にブロックする（一回限りの調査用操作のため
許容する、既存パターンを踏襲）。

新規: `StackTraceRequestModel`/`StackTraceResultModel`
（`src/Srm.Runtime/Sandbox/StackTraceModel.cs`）、`StackTraceOperation`
（`src/Srm.Runtime/Operations/StackTraceOperation.cs`、Tier2専用のホスト側
入口）、`RunCommand.HandleStackTraceRequest`（ゲスト側ハンドラ）。
`DiagCommand.RunStackTraceForApp`のTier2拒否分岐を`StackTraceOperation`
呼び出しへ置き換えた。

【実機検証・重要な発見】実機（Windows Sandbox）で2パターン検証した:
1. アイドルなプロセス（`cmd.exe`が`ping -n 600`で待機中）に対する3秒間の
   採取要求 → 総サンプル0件（プロセスがほぼCPUを使っていないため妥当な
   結果）で完了したが、リクエスト発行から結果が書き込まれるまで約110秒
   かかった。
2. CPUを使い切るビジーループ（PowerShellの`while`ループ）に対する同じ
   3秒間の採取要求 → 4896サンプル採取に成功し、`clr!`/`ntdll!`を含む
   妥当なトップフレームが得られた（機構自体は正しく動作することを実証）。
   ただし、リクエスト発行から結果が書き込まれるまで**約14分**かかった。

Tier1（通常は要求した採取時間+数秒程度で完了）と比べて著しく遅い。
総サンプル0件だったケースでもシンボル解決フェーズには到達しないため
（`Analyze`の`total == 0`早期リターン）、遅延の主因はシンボル解決では
なくETWカーネルセッション自体の確立/停止にあると考えられる。原因は未確定
のままdecisionを「Tier2でも機能はするが、既知の重大な性能特性として
文書化した上で受け入れる」とした。タイムアウトを20分に設定し、CLI側で
事前に「時間がかかる」旨の警告を表示するようにした。


## Rationale

Tier2ゲストVM内でのETWカーネルセッション遅延の根本原因（Windows Sandboxの
ネスト仮想化がハードウェアパフォーマンスカウンタベースのProfileキーワード
サンプリングに影響しているという仮説）を追加調査するには、Windows Sandbox
自体の仮想化実装（Hyper-V統合コンポーネント、パフォーマンスカウンタの
仮想化サポート）を掘り下げる必要があり、srmのコードだけでは検証できない
領域に踏み込む。DC-016が「.NET高レベルAPIがAppContainer環境で想定外の
挙動をする」領域を掘り下げて多大な時間を投じた前例を踏まえ、今回は
「機構自体は正しく動作する」ことを実証した時点で実用上の価値があると判断し、
根本原因の追及より先に、実際に使えるようにする（長いタイムアウト・事前
警告）ことを優先した。将来この遅延が実用上耐えられないほど問題になった
場合に、原因調査を再開する前提でreview_triggerに残す。


## Implications

- 新規: `src/Srm.Runtime/Sandbox/StackTraceModel.cs`・ `src/Srm.Runtime/Operations/StackTraceOperation.cs`
- `src/Srm.Cli/Commands/RunCommand.cs`: `BlockUntilStop`の genericRequestHandlers辞書へ`stacktrace`キーを追加、 `HandleStackTraceRequest`を新規実装
- `src/Srm.Cli/Commands/DiagCommand.cs`: `RunStackTraceForApp`のTier2拒否 分岐を`StackTraceOperation`呼び出しへ置き換え、Tier2実行前に所要時間の 警告を表示するようにした
- `manual/usage.md`の`--stacktrace`節を更新し、Tier2対応と実測レイテンシ （アイドル時約110秒・CPU高負荷時約14分）を明記した
- 自動テストは追加していない（DC-016/DC-020/DC-021と同じ方針。 ETWカーネルセッションは管理者権限・実カーネルトレース基盤を要し、 CI/単体テストでの再現性確保が難しいため、実機検証結果を本レコードに 記録することで担保する）

## Review Triggers

- Tier2でのETWカーネルセッション（Profileキーワード）が、Tier1と比べて 著しく遅い（実測でアイドル時約110秒、CPU高負荷時約14分）根本原因は 未確定のまま。Windows Sandboxのネスト仮想化がハードウェアパフォーマンス カウンタベースのサンプリングに与える影響という仮説はあるが、Microsoft 公式文書等での裏付けは無い。将来この遅延が実用上問題になった場合、 Windows Sandbox側の仮想化実装を掘り下げる調査が必要になる可能性がある
- 現在のタイムアウト（20分）は実測値（約14分）に安全マージンを加えた 値だが、より重いワークロード・より長い採取時間（`--duration-ms`を 大きくした場合）ではこれを超える可能性がある。実際に超過するケースが 見つかった場合、タイムアウトの再調整または進捗表示の追加を検討する
