# [DC-026] Tier2 AppContainerプロセスのsrm diag PID解決失敗を生Win32 API直接クエリで解決し、副産物としてDC-018のSystem.Text.Json版数競合再発も修正

## Context

DC-023/DC-025の実機検証で、`tier2.app_container: true`（既定）のTier2アプリに
対して`srm diag`（既存機能）・`srm diag --watch`（tier2-process-monitor、本
セッションの新規実装）のどちらも、対象PIDを解決できず一貫して失敗する
（`ArgumentException: Process with an Id of X is not running.`）ことが判明
していた。`tier2.app_container: false`（restricted-account-app-isolation
経由）では問題なく動作していたため、AppContainer固有の問題であることは
切り分け済みだったが、原因は未特定のままDC-025のreview_triggerに持ち越して
いた。本レコードはこの継続調査の結果を記録する。

調査の過程で、無関係な既存バグ（DC-018が過去に一度解決した
System.Text.Json/System.IO.Pipelinesの版数競合）が別の経路で再発している
ことも発見し、あわせて修正した。


## Decision

【1. srm diag PID解決失敗の根本原因と解決】
`ProcessMonitorHandler`（新規実装）に一時的な診断コードを追加し、実機で
以下を確認した:
- `Process.GetProcesses()`による列挙には対象AppContainerプロセスのPIDが
  一切現れない（`enumeratedAlive=False`）
- 一方、生の`OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION, false, pid)`は
  エラーコード0（成功）でハンドルを取得できる
- `OpenProcess(PROCESS_QUERY_INFORMATION | PROCESS_VM_READ, ...)`
  （フル権限）も同様に成功する
- `SeDebugPrivilege`を`AdjustTokenPrivileges`で明示的に有効化しても
  （`RestrictedAccountLauncher.EnablePrivilege`と同じ「保持と有効化は別」の
  パターン）挙動は変化しない

これにより、OSレベルのアクセス拒否ではなく、`System.Diagnostics.Process.
GetProcessById`（内部で`GetProcesses()`相当の列挙を行い対象PIDの有無を
確認してから例外を投げる実装）がAppContainerプロセスを認識できないという
.NET側の制約であると判明した。

対象PIDは呼び出し元（`JobObjectManager`経由、または起動時に記録済みの
PID）から常に既知の値として渡されており、「未知のPIDを列挙して発見する」
必要が無い。そこで`DiagCollector`・`ProcessMonitorHandler`の両方を、
`Process`クラスの列挙に依存せず、既知のPIDに対して直接`OpenProcess`する
生Win32 API（`GetProcessTimes`・`GetProcessMemoryInfo`・
`GetProcessHandleCount`・`CreateToolhelp32Snapshot`によるスレッド列挙）
ベースの実装に置き換えた。

実機検証（Tier2、`tier2.app_container: true`）で、`srm diag`・
`srm diag --watch`ともに`Success=true`を返すようになったことを確認した。

【2. 副次的な発見: ハンドル数・スレッド数・ワーキングセットは引き続き
最小値のまま】
PID解決自体は解決したが、`GetProcessHandleCount`・`GetProcessMemoryInfo`・
スレッド列挙は、AppContainerプロセスに対してはエラーを返さず「成功」する
にもかかわらず、実際の値ではなく最小値（ハンドル数0、ワーキングセット
36864バイト固定）を返すことを実機で確認した。上記の通りフル権限での
`OpenProcess`成功・`SeDebugPrivilege`有効化のどちらも効果が無かったため、
srm側の権限不足が原因ではなく、AppContainer分離自体がこれらの詳細を外部の
照会者（管理者/SYSTEM権限であっても）から隠す設計になっていると考えられる
（未確定、review_trigger参照）。一方`GetProcessTimes`（CPU時間）だけは
AppContainerプロセスに対しても正しい値を返すことを確認済みで、DC-016以来
最も重視されてきた指標（カーネルCPU時間の異常検知）のため実用上の価値は
失われていない。

【3. 副産物: DC-018のSystem.Text.Json版数競合の再発を発見・修正】
上記の実機検証を`tools/package.ps1`で結合publishしたバイナリに対して行う
過程で、`srm.exe`が`System.IO.FileNotFoundException: Could not load file
or assembly 'System.Text.Json, Version=10.0.0.0...'`で起動時に即座に
クラッシュする別の問題に遭遇した。これはDC-018が2026-07-03に一度解決した
はずの「同一binフォルダへ複数の自己完結アプリをpublishする際の依存版数
競合」と同じ症状だった。

切り分けの結果、`Srm.PolicyEditor.csproj`（WPFアプリ）が`Srm.Runtime`を
ProjectReferenceしておらず、DC-018がSrm.Runtime.csprojに追加した
`System.Text.Json`/`System.IO.Pipelines`のVersion="10.0.9"固定を一切
受け取っていないことが判明した。単体でpublishすると、フレームワーク既定の
8.0.x版を出力する。`tools/package.ps1`の結合publish順序
（srm.exe→Srm.Mcp.exe→Srm.PolicyEditor.exe→Srm.McpBridgeGuest.exe）で
Srm.PolicyEditorが3番目にこの誤った8.0.x版を書き込むと、4番目の
Srm.McpBridgeGuestが正しい10.0.9版を publishする際、`dotnet publish`の
増分コピー判定が「既存ファイルが既にある」として上書きをスキップし、
誤った8.0.x版が最終的な結合フォルダに残ることを実機で確認した
（単独publish→単独publishの2段階を同一フォルダに対して順に実行する
再現実験で確認済み）。

`Srm.PolicyEditor.csproj`に他3プロジェクトと同一の
`System.Text.Json`/`System.IO.Pipelines` Version="10.0.9"を明示的に
追加し、4プロジェクト全てが同一版数を持つようにして解決した
（DC-018の`implications`が予見していたリスクがSrm.PolicyEditor.csprojで
的中した形）。


## Rationale

.NETの`Process`クラスがAppContainerプロセスを列挙できないという制約自体は
srmから修正できない（.NETランタイム/BCLの内部実装）。しかし、この
プロジェクトの全ての呼び出し元は既に対象PIDを知っており（`RunningApp`・
`JobObjectManager`経由）、「未知のPIDを発見するための列挙」を一度も
必要としていない。生のWin32 APIで既知PIDへ直接アクセスする方式へ切り替える
ことで、.NET側の列挙ロジックを完全に迂回でき、DC-016以来この種の問題を
何度も生んできた「.NET高レベルAPIがAppContainer環境で想定外の振る舞いを
する」というこのプロジェクトの一貫した教訓とも合致する対応になった。

ハンドル数・スレッド数・ワーキングセットが最小値のままである点は追加調査を
打ち切った。フル権限でのOpenProcess・SeDebugPrivilege明示有効化のいずれも
効果が無かったことから、これ以上はAppContainer分離機構そのものの内部実装を
リバースエンジニアリングする領域に入り、投資対効果が見合わないと判断した。
CPU時間という最も価値の高い指標が正しく取得できる状態に到達した時点で
実用上十分とし、残りは既知の制限としてreview_triggerに記録するに留めた。

Srm.PolicyEditorの版数競合修正は、DC-018のimplicationsが明示的に警告して
いた「新しいPackageReferenceが3アプリのいずれかにのみ追加された場合に
再び崩れうる」の裏返しのケース（新しいPackageReferenceの追加ではなく、
既存プロジェクトがそもそも固定を受け取っていなかった）だった。今後同種の
再発を防ぐため、`Srm.Runtime`を参照しない全publishプロジェクトに同じ
固定を明示することにした（Srm.Runtimeを参照させて一元化する方が理想的だが、
Srm.PolicyEditorはSrm.PolicyEngine/Srm.PolicyIntegrityのみに依存する設計を
意図的に保っており、影響範囲の小さい直接固定を選んだ）。


## Implications

- `src/Srm.Runtime/Diagnostics/DiagCollector.cs`・ `src/Srm.Runtime/Diagnostics/ProcessMonitorHandler.cs`を、 `System.Diagnostics.Process`ベースから生Win32 API （`OpenProcess`/`GetProcessTimes`/`GetProcessMemoryInfo`/ `GetProcessHandleCount`/`CreateToolhelp32Snapshot`）ベースの実装へ 書き換えた。公開APIシグネチャ（`Handle(...)`の引数・戻り値）は変更なし
- `src/Srm.PolicyEditor/Srm.PolicyEditor.csproj`に `System.Text.Json`/`System.IO.Pipelines` Version="10.0.9"の PackageReferenceを追加した
- テスト: 既存の`DiagCollectorTests`・`ProcessMonitorHandlerTests`は 書き換え後も無変更のまま全てグリーン（非AppContainerプロセスに対する ThreadCount>0/HandleCount>0のアサーションを含む、回帰なしを確認）
- 実機検証: Tier2（tier2.app_container true）で`srm diag`・ `srm diag --watch`ともにPID解決成功・CPU時間の正しい取得を確認した

## Review Triggers

- 【2026-07-15追加調査・引き続き未解決として打ち切り】AppContainerプロセスに 対して`GetProcessHandleCount`/`GetProcessMemoryInfo`/スレッド列挙が 最小値を返す件について、Win32ラッパーを経由しない`NtQueryInformationProcess` （`ProcessHandleCount`情報クラス、0x20）を直接呼ぶ追加調査を行った。 結果は`STATUS_INFO_LENGTH_MISMATCH`(0xC0000004)で、バッファサイズを ULONG1個（4バイト）・ULONG2個（8バイト、`HandleCount`+ `HandleCountHighWatermark`）のどちらで試しても変化せず、かつ`ReturnLength` が0のまま（通常この状態異常時に期待される「必要なバッファ長を教える」 挙動すら起きない）ことを実機で確認した。これはバッファサイズの問題では なく、OS最下層のAPIレベルでもAppContainerプロセスに対するこの種の照会が 構造的に拒否されていることを示す追加の状況証拠である。Microsoft公式 文書での明示的な裏付けは依然として無いが、Win32ラッパー→NT直接呼び出し という2段階の切り分けを尽くしたため、これ以上の追加調査は投資対効果に 見合わないと判断し、恒久的な既知の制限として本レコードに確定させる （`ProcessMonitorHandler`のコメント参照）
- 【2026-07-15解決】`tools/package.ps1`の結合publish方式が新規プロジェクト 追加のたびに版数競合再発リスクを構造的に抱えていた問題を、運用上の注意 喚起だけでなく自動チェックとして解決した。4プロジェクトのpublish完了後、 各`*.deps.json`が期待するSystem.Text.Json/System.IO.Pipelinesのメジャー バージョンと、`artifacts\publish\`に実際に存在するDLLのアセンブリ バージョンを比較し、不一致があればわかりやすいエラーメッセージ付きで `package.ps1`自体を失敗させるチェックを追加した。実機で、(a)現状（修正 済み）では検出なしで成功、(b)`Srm.PolicyEditor.csproj`の版数固定を 意図的に外すと`FileNotFoundException`の実行時クラッシュではなく packaging時点で明確な差分メッセージ付きで失敗する、の両方を確認した。 これによりこの種のバグはCIでは検証できないままだが、少なくとも package.ps1を実行した時点で（実機のTier2/Channel D検証を待たずに） 即座に検出できるようになった
