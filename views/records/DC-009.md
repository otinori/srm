# [DC-009] WFPホスト許可リストはインストール時にDNS解決してIPベースのフィルタを生成

## Context

ポリシーの `network.allow_hosts` はドメイン名（例: `api.anthropic.com`）の
リストとして宣言される。一方、Windows Filtering Platform (WFP) の
`FWPM_CONDITION_IP_REMOTE_ADDRESS` 条件はIPアドレス単位でしか
マッチングできず、ドメイン名を直接条件として登録する手段がない。


## Decision

`WfpManager.Install()` 実行時（`srm run` 起動時）に `allow_hosts` の各エントリを
DNS解決し、得られたIPアドレスごとに許可フィルタ（AppContainer SID条件 + IP
条件、weight 0xFF）を登録する。ワイルドカード（`*.example.com`）はapex
ドメイン（`example.com`）のみを解決対象とする。


## Rationale

WFPの制約上、ドメイン名ベースのフィルタリングは原理的に不可能なため、
インストール時点でのDNS解決によるIP変換が現実的な実装パス。
v0.1のスコープ（`api.anthropic.com` 等の固定エンドポイントへのアクセス制御）
では、起動のたびに再解決すれば許容できる精度。


## Implications

- CDN等でIPが動的に変わるホストでは、起動時に解決したIPが後で無効になり 通信がブロックされる可能性がある——`api.anthropic.com` 等の主要ホストでの 実運用検証が必要（spec-v01-srm-run 受け入れ基準8.3、Windows実機待ち）
- DNS解決失敗時（名前解決不能）のエラーハンドリングは現状「該当ホストの フィルタを追加しない」動作——明示的な警告ログの追加を検討する余地がある

## Rejected Alternatives

### DNSプロキシ/フッキングによる動的IP登録 (alt-dns-proxy)

AppContainerプロセスのDNSクエリを横取りし、解決されたIPを動的にWFP
フィルタへ追加する方式。CDN利用先（IPが頻繁に変わる）に対してより
正確だが、DNSプロキシ自体の実装・起動順序・障害時のフェイルセーフが
v0.1のスコープに対して過大。PoC（spec-poc-plan PoC-2）でWFPの
SIDベースフィルタリング自体の実現可否を先に検証する方針と矛盾する。


### プロセス名ベースのフィルタリング（WFPを使わない） (alt-process-name-filter)

ドメイン解決の問題を回避できるが、AppContainer単位の隔離という
アーキテクチャ上の前提（spec-srm-architecture）から外れ、同名プロセスを
区別できないなどセキュリティ上の精度が大きく劣化する。
